Everything native is on one global, `host`. There is nothing to import, it is the same object in page and server code (like `Bun`), and its members are reactive in components. It is typed through the one-line `src/host.d.ts` the Vite plugin writes on the first dev run. Commit it.

```svelte
<p>{host.app.name} · {host.theme.dark ? 'dark' : 'light'}</p>
<button onclick={() => host.clipboard.writeText(text)}>Copy</button>
<button onclick={() => host.notifications.show({ title: 'Done' })}>Notify</button>
```

```ts src/lib/server/db.ts
import { Database } from 'bun:sqlite';
import { join } from 'node:path';

// Server code: load functions, remote functions, endpoints, hooks.
export const db = new Database(join(host.paths.data, 'app.db'));
```

The guides show how to build things with it ([windows](/ui/windows), [menus](/ui/menus), [OAuth](/features/oauth)...). This section is the reference: one page per member, with every property, method, event and the platforms it works on.

## How it works

**Stores and services.** Most members are a reactive store with the service of the same name behind it. `host.window.fullscreen` is a reactive boolean you can read in markup or in `$derived`; `host.window.setFullscreen(true)` is the operation that changes it. A few members are services only (`host.dialog`, `host.shell`, `host.webview`...): they have methods, no reactive state.

**Native operations are async.** They return a promise, and when one fails it rejects with a `NativeApiError` whose `code` says why (see [Errors](#errors)). A few helpers are synchronous: subscriptions such as `host.on()` return their unsubscribe function directly, and server helpers such as `host.jobs.start()` return at once. Each page says which.

**Page and server code.** The same calls work in a component and in a load function, a remote function, an endpoint or a hook. A few members exist only in server code (`host.paths`, `host.sidecar()`, `host.jobs.start()`, `host.mcp`...): see [Server code](/host/data/server).

**Outside the app.** In a plain browser tab, or a server running outside the app, `host.available` is `false` and calls reject.

**What the platform supports.** Each page has a support table. At run time, `host.capabilities.describe()` lists every operation of the running build and whether this platform supports it.

## Errors

| Code | Meaning |
| --- | --- |
| `invalid_args` | Bad arguments (unknown menu role, duplicate window label, ...) |
| `unsupported` | The operation can't be implemented on this OS through this backend |
| `unavailable` | Missing at run time (no bundle id, no libnotify, ...) |
| `denied` | Permission refused, or the operation isn't in `bridge.allow` |
| `undeclared` | A permission requested without its `permissions` entry in the config |
| `unknown` | No such operation |
| `internal` | The operation failed |

```ts
try {
  await host.window.setSimpleFullscreen(true);
} catch (e) {
  if ((e as { code?: string }).code === 'unsupported') { /* not on this platform */ }
}
```

## Restricting pages

By default pages may call every operation. `bridge.allow` limits them, enforced natively; server code is never restricted:

```ts desktop.config.ts
bridge: { allow: ['window.*', 'clipboard.readText', 'notifications.*', 'events.emit', 'app.getInfo', 'app.getPath'] },
```

A refused call rejects with `denied`. Rules are `service.op`, `service.*` or `*`, and apply to plugin commands too (`text.*`). Only calls the page makes are checked: events the native side pushes to the page (window events, broadcasts from the server) still arrive.

The list is checked against every operation behind a `host` member, including ones you don't call directly. Several page features go through `events.emit`, so a list without it breaks them silently or with `denied`:

- `host.broadcast`, and everything built on it: `host.jobs` (its first call asks the server for a snapshot), and the refresh of one window's state when another window changes it.
- `host.store`, `host.windowState` and other app files: a page reads and writes them by asking the app server over `events.emit`. Without it they time out after ten seconds, and `host.windowState` also needs `app.getPath`.
- `host.notifications`, which also asks the server over `events.emit`.
- `host.app.info` (and `host.app.name`, `version`...) needs `app.getInfo`.

Add the operations for each member the page uses, or test the page with the list on. Server code is unaffected, so the same members work from an endpoint or remote function.

## Imports instead of the global

The same API is available as modules, for those who prefer imports:

- `@svelte-desktop/shell/stores`: the reactive stores.
- `@svelte-desktop/shell/platform`: the services and `broadcast`. `NativeApiError` is exported from here too.
- `@svelte-desktop/shell/native`: `native`.
- `@svelte-desktop/shell/server` and `@svelte-desktop/shell/client`: server-only and page-only helpers.

```ts
import { theme, window } from '@svelte-desktop/shell/stores';
import { popover, broadcast } from '@svelte-desktop/shell/platform';
```
