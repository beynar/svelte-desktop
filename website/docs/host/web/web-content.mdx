These members of `host.webview` control what web views load and which scripts run in their documents. Rules, the script registry and [custom protocols](/host/web/protocol) are global across [sessions](/host/web/sessions); a session does not isolate their configuration. Script targets can narrow injection to particular views.

How-to: [Web view](/ui/web-view#declarative-request-rules).

## Methods

### `setContentRules(options)`

Compile and install a WebKit content-blocker list for every existing and future window, popover and embedded view. On Windows the same format is matched by the shell: see [Rules on Windows](#rules-on-windows).

```ts
await host.webview.setContentRules({
  id: 'privacy',
  rules: [{
    trigger: { 'url-filter': 'https://tracking\\.example/.*' },
    action: { type: 'block' },
  }],
});
```

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `id` | `string` | Required | List identifier, 1–256 characters. |
| `rules` | `ContentRule[]` | Required | Nonempty list of rules, described below. |

Resolves `null` after compilation. Reusing an `id` replaces the previous list only after successful compilation. A replacement or removal during compilation rejects the superseded call with `unavailable`. Invalid rules, unsupported actions and compilation errors reject with `invalid_args`; an app origin that is not ready gives `unavailable`.

Rules affect subsequent requests, including requests from existing documents. They last for this app run. The shell adds exceptions for its own origin and event WebSocket, so rules cannot block the app's documents, resources or bridge.

macOS, Linux and Windows.

#### `ContentRule`

Each rule has a `trigger` object and an `action` object. Filters use WebKit's restricted regular-expression syntax.

| Trigger field | Type | Default | Description |
| --- | --- | --- | --- |
| `url-filter` | `string` | Required | URL regular expression. |
| `url-filter-is-case-sensitive` | `boolean` | WebKit default | Whether URL matching is case-sensitive. |
| `resource-type` | Array of resource types below | All resource types | Restrict matched resources. |
| `load-type` | `('first-party' \| 'third-party')[]` | Both | Restrict by relation to the document. |
| `if-domain` | `string[]` | No positive domain condition | Match these domains; unavailable for CSS hiding. |
| `unless-domain` | `string[]` | No domain exclusion | Exclude these domains. |
| `if-top-url` | `string[]` | No positive top-URL condition | Match these top-document URL filters; unavailable for CSS hiding. |
| `unless-top-url` | `string[]` | No top-URL exclusion | Exclude these top-document URL filters. |

Resource types are `document`, `image`, `style-sheet`, `script`, `font`, `raw`, `svg-document`, `media`, `popup`, `ping`, `fetch`, `websocket` and `other`.

| Action field | Type | Default | Description |
| --- | --- | --- | --- |
| `type` | `'block' \| 'block-cookies' \| 'css-display-none' \| 'make-https' \| 'ignore-previous-rules'` | Required | Block a resource, suppress cookies, hide matching elements, upgrade to HTTPS, or exempt a match from earlier rules. |
| `selector` | `string` | Required for `css-display-none` | CSS selector to hide. Other action variants have no `selector` field. |

CSS hiding needs an app-origin exclusion directly in its trigger: WebKit cannot reliably undo it with `ignore-previous-rules`. For `css-display-none`, positive `if-domain` and `if-top-url` conditions reject with `invalid_args`. Native validation also rejects frame-URL conditions. Use either `unless-domain` or `unless-top-url`, not both; when supplied, the array must be nonempty. CSS domain exclusions must be nonempty lowercase ASCII or punycode. The shell converts domain exclusions to top-URL exclusions and adds its own origin. CSS hiding is not a security boundary.

Other actions retain WebKit's normal condition validation. This is not Electron's `webRequest`: the API has no arbitrary per-request callback, no HTTP header/body rewriting and no complete subresource telemetry.

### `listContentRules()`

Resolves `{ id, rules }[]`: the lists in place, with the rules as given. The reactive field `host.webview.contentRules` holds the same list and updates when you set or remove one. macOS, Linux and Windows.

### `removeContentRules(id)`

Remove a list from all web views and cancel any in-flight replacement for that `id`.

```ts
await host.webview.removeContentRules('privacy');
```

`id: string` must contain 1–256 characters, otherwise the call rejects with `invalid_args`. Resolves `null`, including when no list has that identifier. macOS, Linux and Windows.

### `scripts.register(script)`

Register a `UserScript` for future documents, including later navigations in existing views.

```ts
await host.webview.scripts.register({
  id: 'reader',
  source: 'globalThis.readerInstalled = true',
  timing: 'start',
  world: 'reader',
  mainFrameOnly: true,
  target: { viewId: 'article' },
});
```

| `UserScript` field | Type | Default | Description |
| --- | --- | --- | --- |
| `id` | `string` | Required | Identifier, 1–256 characters. |
| `source` | `string` | Required | JavaScript source. |
| `timing` | `'start' \| 'end'` | Required | Inject at document start or document end. |
| `world` | `'page' \| string` | Required | `page` shares page globals; another name selects a named content world. Must contain 1–256 characters. |
| `mainFrameOnly` | `boolean` | `true` | Inject only in the main frame. |
| `target` | `WebviewTarget` | Every existing and future web view | Optional target filter, across all sessions. |
| `target.windowId` | `number` | No window filter | Public window id; `0` is the main window. |
| `target.popoverId` | `string` | No popover filter | Popover identifier. |
| `target.viewId` | `string` | No embedded-view filter | Embedded-view identifier. |

Every supplied target field must match. These are registry filters, not the single-view precedence rules used by [core web-view methods](/host/web/webview#targets).

Resolves `null`. Invalid required fields or target shapes reject with `invalid_args`. Reusing an `id` replaces that script while retaining its registration order. Registration does not evaluate the script in the current document. The shell preserves its own bridge scripts when updating the registry.

macOS, Linux and Windows.

### `scripts.unregister(id)`

Stop future injection of a registered script.

```ts
await host.webview.scripts.unregister('reader');
```

`id: string` must contain 1–256 characters, otherwise the call rejects with `invalid_args`. Resolves `null`, including for an unknown identifier. Existing document effects are not undone. macOS, Linux and Windows.

### `scripts.list()`

Return the global registry in registration order.

```ts
const scripts = await host.webview.scripts.list();
```

Resolves `UserScript[]`, with the fields described above. Native records include the resolved `mainFrameOnly` default. macOS, Linux and Windows.

### `setNavigationPolicy(policy)`

**Server only.** Install one asynchronous navigation veto, or pass `null` to remove it.

```ts
// src/hooks.server.ts
await host.webview.setNavigationPolicy(({ url }) =>
  new URL(url).hostname === 'unwanted.example' ? 'cancel' : 'allow'
);
```

`policy` is `NavigationPolicy | null`. A `NavigationPolicy` receives a `NavigationRequest` and returns `'allow' | 'cancel'`, directly or through a promise.

| `NavigationRequest` field | Type | Description |
| --- | --- | --- |
| `url` | `string` | Requested navigation URL. |
| `isMainFrame` | `boolean \| null` | Whether the navigation targets the main frame. `null` on Linux, where WebKitGTK doesn't say when it asks. |
| `viewId` | `string` | Embedded-view id, popover id, or `window:` followed by the public window id. |

Resolves `void` after installation. Calling from a page rejects with `denied`. Replacing or removing the policy cancels pending decisions. A thrown/rejected handler, an answer other than `allow`, or a ten-second timeout cancels the navigation.

The shell's existing navigation checks still apply: `allow` cannot bypass them. App-origin navigation is exempt. The policy covers navigations, not fetches or other subresources, and is shared across sessions. It runs in the Bun Worker in packaged apps and in the Vite server during development.

macOS, Linux and Windows. See [Platform support](#platform-support).

## Content worlds

Named `WKContentWorld` instances share the DOM but have separate JavaScript globals. A named world cannot see page globals, `host` or the shell bridge; the page cannot read its globals. DOM changes remain visible across worlds, so this is not a general sandbox for hostile code.

To run code in a named world, pass `world` to [`executeJavaScript(code, target)`](/host/web/webview#executejavascriptcode-target). It defaults to `page` and executes in the main frame. Named-world execution through `executeJavaScript` is macOS only: registered scripts can use a named world on Linux and Windows too.

## Platform support

| Method | macOS | Linux | Windows |
| --- | --- | --- | --- |
| `setContentRules`, `removeContentRules`, `listContentRules` | ✓ | ✓ | ✓³ |
| `scripts.register`, `scripts.unregister`, `scripts.list` | ✓ | ✓ | ✓⁴ |
| `setNavigationPolicy` | ✓ | ✓² | ✓¹ |

1. On Windows only embedded views are asked, main frame and frames; `<a download>` links aren't. WebView2 can't defer a navigation, so the UI thread waits for the answer with a nested message loop, for ten seconds at most. Platform calls keep working meanwhile, but WebView2's own callbacks wait: a policy that needs one, such as `executeJavaScript`, runs into the deadline and the navigation is canceled. A refused request gets a local answer, so it doesn't reach the server.
2. On Linux views, windows and popovers are asked, frames too, and `isMainFrame` is `null`. A refused navigation sends no request. Because the frame isn't known, a window's scripted navigation to another origin is asked as well, where macOS sends it to the browser at once: `allow` still ends in the browser.
3. See [Rules on Windows](#rules-on-windows).
4. A `page` script runs through `AddScriptToExecuteOnDocumentCreated`, and a named world's through the DevTools protocol, so it really has its own globals. A script with `timing: 'end'` runs in a function on `DOMContentLoaded`, so its `var`s aren't page globals; with `timing: 'start'` they are.

### Rules on Windows

WebView2 has no content blocker. The shell matches the same JSON from `WebResourceRequested`, on every resource of every web view, on the UI thread. That handler is only installed while a list with something other than `css-display-none` exists: an app with no rules pays nothing. On the test runner, a page of 400 images took 30 to 50% longer under 200 rules, 0.3 to 0.5 ms per request, and all of them arrived. Filters are compiled once, to a matcher whose time depends on the URL's length and not on the pattern.

The filter syntax is WebKit's: `.`, `[...]`, groups, `*`, `+`, `?`, `\\x` for a literal, `^` at the start and `$` at the end. Anything else rejects with `invalid_args`, as it does on macOS: no `|`, no `{n}`, no `\\d`.

What's refused with `invalid_args`, since WebView2 can't do it and a rule that does nothing would look like one that works:

- `block-cookies`. WebView2 adds a request's cookies after the handler has run: a real server still received them with the header taken away.
- `resource-type: ['websocket']`. WebView2 doesn't raise the event for a WebSocket. A rule without a `resource-type` is accepted and doesn't stop one either: a real socket connected under `block` on its URL. This is the one thing a rule silently leaves out.
- `resource-type: ['popup']` and `['svg-document']`. A popup never opens in a web view here, and an SVG document's request looks like any other's.
- `if-frame-url`, `unless-frame-url`, `load-context` and any other trigger: the handler doesn't say which frame asks.
- On a `css-display-none` rule, `resource-type` and `load-type`. See below.

What behaves differently:

- `block` answers a local 403 with no body: the server gets nothing. An image or a script fails. A same-origin `fetch()` resolves with status 403 instead of rejecting. A blocked page fails to load: a view reports `viewFailed` and shows WebView2's error page.
- `make-https` answers a 307 to the same URL over HTTPS, keeping the port.
- `css-display-none` is a script in each document. It looks at the document's own URL, not at the resources it loads. In a frame on another origin, `unless-domain` and `unless-top-url` see the top page's origin only. It takes effect from the next document, and a page's Content-Security-Policy doesn't stop it. An invalid selector is dropped without an error.
- `load-type`: first party means the same registrable domain as the top document. There's no public suffix list here: the last two labels, or three under a two-letter country code when the label before it is short (`a.co.uk`). IP addresses must be equal.
- A dedicated worker's requests are matched like the page's; on a runtime before `ICoreWebView2_22`, they aren't.

## Example

Register before navigation so the next document receives the script. This assumes a view created with `id: 'article'` (see [`host.view.create`](/host/windows/view)).

```ts
await host.webview.scripts.register({
  id: 'article-marker',
  source: "document.documentElement.dataset.reader = 'on'",
  timing: 'end',
  world: 'reader',
  target: { viewId: 'article' },
});
await host.webview.reload({ viewId: 'article' });
// Later, stop injection in subsequent documents:
await host.webview.scripts.unregister('article-marker');
```

For per-origin consent, HTTP authentication and certificate exceptions, see [web policy](/host/web/web-policy).
