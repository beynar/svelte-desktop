title: Testing
description: Drive the real app window from bun test, built or under vite dev.
---

`@kitop/shell/test` launches the app in its real window and drives it from `bun test`: DOM interactions in the page, any native op, screenshots and native events.

```ts tests/app.test.ts
import { afterAll, beforeAll, expect, test } from 'bun:test';
import { launch, type AppHandle } from '@kitop/shell/test';

let app: AppHandle;
beforeAll(async () => (app = await launch(process.env.DESKTOP_TEST_DEV ? { dev: true } : {})));
afterAll(() => app?.close());

test('adds a note', async () => {
  await app.fill('input[name=text]', 'hello');
  await app.press('input[name=text]', 'Enter');
  await app.waitFor(() => document.body.innerText.includes('hello'));
});

test('native window', async () => {
  expect(await app.platform('window', 'getTitle')).toBe('Notes');
});

test('native plugin', async () => {
  expect(await app.platform<string>('greeter', 'hello', { name: 'test' })).toContain('Hello');
});
```

```sh
bunx --bun vite build
bun test --timeout 30000 tests/
```

App startup exceeds Bun's 5 second default timeout, hence `--timeout`. Without options, `launch()` runs the first built app in `.desktop/dist`, so build first. A build signed to be distributed (a real macOS identity, or Windows signing) can't be driven this way, so no other program can use the app's identity: to test one, build it with `KITOP_TEST_BUILD=1`, and don't ship that build. `DESKTOP_TEST_DEV` is this example's own convention for choosing `{ dev: true }`, not a framework variable. The `greeter` test calls an op of your own native plugin.

`launch()` opens a real window, which takes input focus while the tests run. In CI the machine needs a display: a logged-in session on macOS, a virtual one such as Xvfb on Linux.

## The app handle

| | |
| --- | --- |
| `click(selector)`, `fill(selector, value)`, `press(selector, key)` | DOM interactions |
| `text(selector?)` | Text content |
| `waitFor(selectorOrPredicate, { timeout })` | Wait for a selector, or a page function returning truthy (default timeout 10 s) |
| `eval(code or fn, ...args)` | Evaluate in the main window's page; promises awaited, JSON result |
| `goto(path)` | Navigate (client-side when SvelteKit handles the link) |
| `platform(service, op, args)` | Any native op |
| `nextEvent(name, filter?, timeout?)` | The next native event matching `filter` |
| `screenshot(path?)` | PNG of the page |
| `origin`, `stdout` | The app's server origin and its output |
| `close()` | Quit the app |

`click`, `fill` and `press` run JavaScript in the page. They do not send OS input: `press` dispatches keyboard events, and for `Enter` also submits the element's form. Use `platform()` for native operations. Page functions passed to `eval()` or `waitFor()` are serialized; pass values as `eval()` arguments rather than capturing local variables.

The test channel is enabled by `KITOP_TEST`, which `launch()` sets. A built app can connect when that variable is supplied; a normal launch without it exposes no test channel. A build made to be distributed has none at all: `kitop build --release` on any OS, or a signed build unless `KITOP_TEST_BUILD=1`. Run your tests on a plain `kitop build`. See [Builds you distribute](/concepts/security#builds-you-distribute). With `connect`, your callback must set the variable on the app it starts. `stdout` is empty in that mode.
