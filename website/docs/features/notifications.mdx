One API, `host.notifications`, on macOS, Linux, Windows and in a plain browser tab.

```ts
await host.notifications.show({
  id: 'msg-42',                 // dedupe: the same id replaces, never duplicates
  title: 'Alice', body: 'Lunch?',
  url: '/chat/42',              // a click opens it in the window that showed it
  data: { chat: 42 },           // handed back in events and lists
  actions: [{ id: 'reply', title: 'Reply', input: { placeholder: 'Message' } }],
});

host.notifications.on('click', (e) => { /* e.id, e.data, e.url; e.preventDefault() skips the navigation */ });
host.notifications.on('reply', (e) => send(e.data.chat, e.input));
```

`show` resolves `{ id, scheduled }` and rejects when the OS refuses. With `replace: false`, an existing id resolves `{ id, scheduled: false, skipped: true }`. Ask for permission with `await host.notifications.requestPermission()` before showing the first notification.

| Platform | Requirements and limits |
| --- | --- |
| macOS | Shown by the built app only: in `vite dev`, `show` does nothing and resolves `skipped: true`, the permission is `'unavailable'`, and one line in the console says so. Actions support text replies. `urgency: 'critical'` maps to time-sensitive presentation, not Apple's critical-alert entitlement. |
| Linux | Needs `libnotify` and a running notification daemon. Text-input actions become plain actions; inline replies are unavailable. |
| Windows | Uses native toasts, with tray balloons as a fallback. Reply input and OS scheduling need the toast backend. |
| Browser | Needs the Notification API and permission. Actions depend on service-worker and browser support. Scheduled notifications need the page to stay open; `repeat` rejects with `unsupported`. |

## Behavior

- **Dedupe.** An `id` replaces a local delivered or pending notification (`replace: false` keeps the existing one). `renotify: false` suppresses the replacement sound on Linux and the popup on Windows; macOS ignores it. Self-hosted pushes share these ids; replacing an APNs notification with a local one of the same id is not guaranteed.
- **Deep links.** `url` (or an action's `url`) navigates with the SvelteKit router; the app's own scheme goes through `host.deepLink`; http(s) opens in the browser.
- **Cold start.** A click that launched the app is kept until the page starts, then navigates; recent responses wait for their first listener. Server code receives responses too, with `host.notifications.on('response', fn)`.
- **Several windows.** Listeners and navigation run in one page: the window that showed it, else the focused one, which comes to the front.
- **Foreground.** On macOS, banners show while the app is frontmost (config `notifications.foreground`, default `true`; per notification `foreground`). Linux and Windows do not implement foreground suppression.

## Scheduling

```ts
await host.notifications.show({ id: 'standup', title: 'Stand-up', at: tomorrow9am, repeat: 'day' });
await host.notifications.show({ title: 'Tea is ready', delay: 4 * 60_000 });
```

`at` (a `Date`, epoch ms or string) or `delay` (ms), with `repeat`: `minute`, `hour`, `day`, `week`, `month`, `year`. `repeat` requires `at` or `delay`. Schedules survive the app quitting on macOS and Windows; Linux keeps the queue on disk and catches up at the next start. macOS repeats use calendar matches; if the next match would fall before `at`, `show()` rejects with `invalid_args` rather than delivering early. Windows queues up to 128 occurrences over the next 30 days and replenishes the queue while the app runs; it cannot repeat indefinitely while closed.

## Events and lists

| | |
| --- | --- |
| `on('click' \| 'action' \| 'reply' \| 'dismiss' \| 'response', fn)` | `{ id, kind, actionId, input, url, data, target, preventDefault() }`; `response` receives every kind |
| `on('shown', fn)` | Delivered while the app runs (a scheduled one firing, a push in the foreground) |
| `delivered()`, `pending()` | Delivered notifications known to the backend, and scheduled ones; Linux tracks notifications from the running app rather than querying the daemon's history |
| `dismiss(id)`, `dismissAll()` | Remove delivered and cancel pending |
| `setBadge(count)` | App icon badge (Dock, Unity launchers on Linux, Windows overlay); `null` or `0` clears it |
| `permission`, `requestPermission()` | Reactive `granted`, `denied`, `notDetermined` or `unavailable`; `requestPermission()` resolves `{ status }` |

## Remote push

`host.push.register()` returns the target your server sends to:

| Platform | Provider | Config |
| --- | --- | --- |
| macOS | APNs | `push: { apns: true }`, a signed app and a provisioning profile with Push Notifications (`sign.provisioningProfile`). |
| macOS, Windows, Linux | Your own push server (Web Push) | `push: { server: 'https://push.example.com' }`. Takes precedence over APNs on macOS. |
| Browser tab | Web Push | `host.push.register({ vapidPublicKey })` |

```ts
const target = await host.push.register();
await saveTarget(target); // your own helper: send it to your server
host.push.on('message', (m) => { /* a push received while the app runs */ });
host.push.on('token', (t) => saveTarget(t)); // rotations
```

Taps on pushes are ordinary notification clicks, with the same `url` and `data`.

### Sending from Bun

No dependencies; one sender for APNs and Web Push (your own push server included):

```ts server.ts
import { createPush } from '@svelte-desktop/shell/push';

const push = createPush({
  apns: { teamId, keyId, key: await Bun.file('AuthKey.p8').text() },
  webpush: { publicKey, privateKey, subject: 'mailto:ops@example.com' },
});

const results = await push.sendMany(targets, { id: 'msg-42', title: 'Alice', body: 'Lunch?', url: '/chat/42' });
// a failed result with expired: true means the target is gone (uninstalled, unsubscribed): delete it
const gone = results.filter((r) => !r.ok && r.expired);
```

`push.send(target, notification)` sends one. `generateVapidKeys()` from the same module creates the Web Push keys. A notification also takes `subtitle`, `data`, `badge`, `sound`, `silent`, `group`, `image`, `ttl`, `priority` and `background` (data-only, delivered to `host.push.on('message')`). APNs images need a notification service extension; passing `image` alone only supplies the image for Web Push.

### Self-hosted push

No Apple account needed: set `push.server` to a Web Push compatible service you run; the app holds one connection while it runs (window closed included, with `quitOnLastWindowClosed: false`). `register()` then returns a Web Push target and the same `push.send()` delivers to it, end-to-end encrypted.

Run the server anywhere with Bun:

```ts push-server.ts
import { servePush } from '@svelte-desktop/shell/push-server';

servePush({ port: 47123, publicUrl: 'https://push.example.com', db: 'push.sqlite' }); // db defaults to ':memory:'
```

`publicUrl` is the origin clients reach the server at. It builds the endpoints and the VAPID audience; without it they come from the request's origin, which is wrong behind a proxy that terminates TLS. `db` defaults to `:memory:`, where queued messages are lost on restart: use a file in production.

Or deploy `packages/push-worker` from the repository on Cloudflare (`bunx wrangler deploy`): one Durable Object per device with hibernatable WebSockets.

In a plain browser tab, notifications use the Notification API and a small service worker served at `/__desktop/push-sw.js`, in its own scope. Web Push needs HTTPS or localhost and service-worker support. Self-hosted desktop push receives messages only while the app process runs; APNs can deliver visible notifications while the macOS app is closed.
