:::note
API reference: [`host.view`](/host/windows/view), [`host.windows`](/host/windows/windows), [`host.menu`](/host/input/menu).
:::

`<WindowTabs>` is the window's tabs, in the title bar, configured by its props and drawn with snippets. Its tabs are your SvelteKit routes: you write links as usual, and the tabs follow. With [`split`](#split-panes), the window divides into panes the user arranges by dragging.

Tabs inside a page need no component: they are plain Svelte, and [`host.store`](/host/data/store) can save them for the next launch.

## The window's tabs

One declaration, in the root layout (`Sidebar`, `AppShell` and `RouteIcon` in the snippets below stand for your own components). `page` is the layout's `children`; `layout` puts the bar in the title bar and the content where the page goes:

```svelte src/routes/+layout.svelte
<script lang="ts">
	import { WindowTabs } from '@kitop/shell/tabs';

	let { children } = $props();
</script>

<WindowTabs page={children} newTab="/" keepAlive={['/chat', '/terminal/[id]']}>
	{#snippet layout({ bar, content })}
		<header class="titlebar">{@render bar()}</header>
		<Sidebar />
		<main>{@render content()}</main>
	{/snippet}
</WindowTabs>

<style>
	.titlebar {
		height: max(var(--desktop-titlebar-height, 0px), 2.75rem);
		padding-left: max(var(--desktop-controls-width, 0px), 0.75rem); /* clear the traffic lights */
		--app-region: drag; /* its empty parts move the window */
	}
</style>
```

Each page names its tab with its `<title>`, like in a browser:

```svelte src/routes/invoices/[id]/+page.svelte
<svelte:head><title>Invoice {data.invoice.number}</title></svelte:head>
```

In a [popover](/ui/menu-bar-and-popovers), `<WindowTabs>` renders the page alone, with no tab bar.

From there, it's links:

```svelte
<a href="/reports">Reports</a>                 <!-- the active tab goes to /reports -->
<a href="/reports" target="_blank">Reports</a> <!-- a new tab (⌘-click, a middle click: in the background) -->
<a href="/chat">Chat</a>                       <!-- /chat is keepAlive: its own tab, which keeps running -->
```

| You | The tabs |
| --- | --- |
| A link, `goto()`, the sidebar | The active tab goes there — the page you leave is unmounted, as on any SvelteKit navigation |
| `target="_blank"` / ⌘-click, middle click | A new tab on it, in front / in the background — on a `keepAlive` route too: another one, with its own view, running from the start (in the background too) |
| A link or `goto()` to a `keepAlive` route | Its tab if it's open, else a new one: it runs in its own web view and goes on while you're elsewhere (timers, sockets, what you typed). The page you were on stays on screen until the view is drawn, then the window's address becomes the tab's: `page.url`, your sidebar's active link, follow it |
| ⌘T / the + button | A new tab on `newTab` |
| ⌘W / × | Close the tab (`beforeClose` can keep it); the main window keeps a tab on `newTab` |
| Drag a tab | Reorder. A regular route tab can move to another window's bar; with at least two tabs, dragging it outside opens a new window. Kept-alive and external tabs stay in their window |
| Back / Forward | The browser's history, shared by the tabs |

You never create a tab by hand. A route that must keep running is declared once, in `keepAlive`, with SvelteKit's route ids (`/terminal/[id]`, `/docs/[...rest]`), and every link to it follows.

- Each kept-alive tab uses another web view and consumes more memory: keep it for pages that need to stay mounted. Hidden views can still be throttled, and suspension or a process crash loses in-memory state. Put work that must outlive a page in [background jobs](/native/jobs) or [services](/native/services).
- While one is shown, the window takes its address without navigating there (no `load`, no page code in the window: the view runs the page), and `page.url`, your sidebar's active link, Back and Forward follow.
- A link followed from your layout while it's shown (the sidebar) goes to a tab of the page: the one already at that address, else the last one shown.

The main window's tabs are restored at the next launch:

- A regular active tab: the window opens on its page.
- A kept-alive active tab: the window opens on the last regular page, then shows the tab's view when ready. Restored kept-alive tabs start after the window page hydrates, subject to `maxViews`.
- The window title follows the active tab.
- A native **Tab** menu has ⌘T ⌘W ⇧⌘T ⌃⇥ and ⌘1–9 (in its **Select Tab** submenu). It wins over the page and over a kept-alive tab's view, and only the focused window acts on it. On Linux and Windows these use Ctrl, and Ctrl+9 selects the last tab.
- With `titleBarStyle: 'hiddenInset'` the bar sits next to the traffic lights: tabs and buttons stay clickable, the empty parts of the strip move the window.

### Snippets

```svelte
<WindowTabs page={children} newTab="/">
	{#snippet tab({ tab, active, close })}
		<RouteIcon path={tab.path} />
		<span>{tab.title}</span>
		<button onclick={close}>✕</button>  <!-- a control in a tab doesn't activate it -->
	{/snippet}

	{#snippet layout({ bar, content, api })}
		<header class="titlebar">{@render bar({ class: 'my-tabs', label: 'Open pages' })}</header>
		<AppShell title={api.active?.title}>
			{#snippet headerActions()}
				<button onclick={() => api.open('https://svelte.dev/docs')}>Docs</button>
			{/snippet}
			{@render content({ class: 'h-full' })}
		</AppShell>
	{/snippet}

	{#snippet embedded({ page })}
		<div class="p-6">{@render page()}</div>
	{/snippet}
</WindowTabs>
```

- `tab` draws each tab (default: its title and a close button).
- `layout` gets `bar` (the tab bar: `class`, `label`, `start`, `end`), `content` (the page, and each kept-alive tab's view in the same place) and `api`; without it, the bar goes above the content.
- `embedded`: a kept-alive tab's view runs your app again, layout included — there, and in a popover, `<WindowTabs>` renders the page alone (or this snippet), on the server too (the view's request says so), so the view shows at its first paint. Your own code can test `embedded` from `@kitop/shell/tabs` (in the page).

`api` is available as `bind:api` in the browser, and as the `api` argument of the `layout` snippet on the server. It has: `items`, `active`, `open(path | url, { background, reuse })` (`reuse: false`: another tab on a kept-alive route already open), `close(id?)`, `activate(id)`, `reopen()`, `cycle(1 | -1)`, `move(id, index)`. `api.open('https://…')` shows another site in a tab of its own (external links keep opening the browser); it can't call native APIs and receives none of the app's events. A tab is `{ id, path?, url?, title? }`. Reuse of a kept-alive tab matches the pathname, ignoring query and hash; it activates the existing tab without changing its URL. Use `reuse: false` to open a separate tab with different parameters.

A view is drawn over the page: your page's popovers and dialogs can't cover a kept-alive tab or another site. A kept-alive tab's view is see-through: where its page paints nothing, the background of your layout around `content` shows — give the `embedded` page no background of its own and it blends in. It waits for its page-ready signal (or a load failure or three-second timeout); until then the tab you were on stays. A link to a kept-alive route starts loading that tab's view when SvelteKit would preload the link, so the click shows it at once: `data-sveltekit-preload-data="hover"` (the default in `app.html`) preloads once the pointer rests on the link, `"tap"` when it is pressed, `"false"` never. A preloaded view that goes unused is dropped after 5 s; at launch, restored kept-alive tabs start once your page is up.

## Split panes

`split` turns the window's tabs into panes, each with its own bar. The user drags a tab to a side of a pane to split it, and the window shows several pages side by side. Every tab runs in its own web view, in its own process on macOS and Linux. On Windows they share one WebView2 environment, which may run several of them in one renderer process, so a page that hangs can take others along:

```svelte src/routes/+layout.svelte
<script lang="ts">
	import { WindowTabs } from '@kitop/shell/tabs';
	import Sidebar from '#lib/Sidebar.svelte';

	let { children } = $props();
</script>

<WindowTabs page={children} newTab="/" split>
	{#snippet layout({ content })}
		<div class="shell">
			<Sidebar />
			{@render content({ class: 'panes', bar: { class: 'pane-bar', label: 'Open pages' } })}
		</div>
	{/snippet}

	{#snippet embedded({ page })}
		<main class="page">{@render page()}</main>
	{/snippet}
</WindowTabs>
```

`content` draws the panes, bars included: `bar` passes the bars' `class`, `label`, `start` and `end`. There's no `bar` to place in `layout`. `embedded` is what each tab's web view shows, since your app runs again in it, so your sidebar isn't drawn there.

The panes fill the box they're given and have no look of their own, so give them a height, and the bars theirs. Inside a layout that sizes to its content, like a page shell, its content has to pass a height down: without one no page shows, and a warning says so in dev. In a global stylesheet (a component's `<style>` would remove these as unused):

```css src/app.css
.shell { display: flex; height: 100vh; }
.panes { flex: 1; min-width: 0; }
.pane-bar { height: 34px; padding: 0 6px; gap: 2px; }
[data-sd-pane][data-top] > .pane-bar { --app-region: drag; } /* the top row moves the window */
/* Without a sidebar, with `titleBarStyle: 'hiddenInset'`: clear the traffic lights. */
[data-sd-pane][data-top][data-left] > .pane-bar { padding-left: max(var(--desktop-controls-width, 0px), 6px); }
```

| The user | What happens |
| --- | --- |
| Drags a tab to a side of a pane | A new pane on that side. The pane's view makes room while the tab is over it, showing where the new pane goes |
| Drags a tab to the middle of a pane, or onto its bar | The tab joins that pane |
| Drags a tab along the bottom, left or right edge of the panes | A new pane along that whole side of the window |
| Drags a tab out of the window | An app route opens in a new window, its page starting again |
| Presses Escape while dragging | Nothing moves |
| Drags the line between two panes | Resizes those two, down to `minPaneSize`; Escape puts them back. With the focus on it: the arrow keys, Home and End. A double click makes the two equal |
| Clicks in a pane | That pane has the focus: the window's title and address are its active tab's |
| ⌘\\ / ⇧⌘\\ | Split right / down, on `newTab` |
| ⌘⌥] / ⌘⌥[ | The next / previous pane |
| ⌘T, ⌘W, ⌃⇥, ⌘1–9 | As usual, within the pane in focus. A pane goes with its last tab, and its room goes back where it came from: the pane it was split from, or all of them for a whole side |

Every tab runs your app again, so three things change for a page in a pane. A module's state is its own: use `host.broadcast` or your server to share it with the other tabs and the window's sidebar. A page that scrolls in its own element instead of the document doesn't get its position back on Back, as in any SvelteKit app. `100vh` is the pane's height, not the window's: a page that subtracts the window's chrome from it needs a minimum. The window's own things (its material, its title bar) are in the window's page: ask it with `host.broadcast`.

A tab moved to another pane keeps its page: it's still running, with what the user typed, its timers and its sockets. Only where its web view is changes, so the page can't tell it moved.

Links work as they do with one pane:

```svelte
<a href="/reports">Reports</a>                 <!-- the active tab of the pane in focus goes there -->
<a href="/reports" target="_blank">Reports</a> <!-- a new tab in that pane (⌘-click: in the background) -->
<a href="/chat">Chat</a>                       <!-- a keepAlive route: its open tab, wherever it is -->
```

In the window's page, a handler can still cancel a link with `preventDefault()`, `data-sveltekit-replacestate` and `data-sveltekit-reset` reach the tab, and `data-sveltekit-reload`, `rel="external"` or `target="_self"` loads the tab alone. A link to where the tab already is runs its `load` functions again.

If the tab's page cancels a navigation of the window's page in `beforeNavigate`, the window's history goes back to what it was.

A link out of the app in a tab's page opens in the browser or the mail client, and the page stays. A full load to another site (`location.assign`) takes the tab there.

A `goto()` in the window's page reaches the tab with its options: `replace`, `state` (a `Date` stays one) and `shallow`. A tab opened or loading for it gets the state once it's hydrated, unless another navigation or its closing comes first. In a tab's page, `host.*` is about that page: `host.webview.reload()` reloads it alone, a rect given to `host.popover.show()` is in it, and a click on a notification it showed comes back to it, with its tab on screen and its window in front. The menu's Edit, Reload and Zoom items are about the page with the keyboard.

The same goes for links in a tab's own page, which stay in its pane, except a link or `goto()` to a `keepAlive` route, which goes to that route's tab: the navigation is canceled, and the page stays as it is. Three cases can't be canceled in time, so the tab itself goes to the new page: a full load (`location.assign`), a redirect from a `load` function, and a link or `goto()` while another page of that tab is still loading. `keepAlive` only says which routes get one tab: all of them keep running. To keep memory down, set `maxViews`: tabs not on screen beyond it are suspended, and a tab on screen never is. So `maxViews={2}` with two panes on screen runs nothing in the background.

From your code, `api` has the tabs as usual, and `api.panes` the panes:

```ts
api.open('https://svelte.dev/docs', { split: 'right' }); // a new pane beside the one in focus
api.open('/reports', { pane: api.panes.panes[0].id });   // in a given pane
api.split('bottom');                                      // `newTab`, in a new pane below
api.focus(paneId);
api.focusPane(1);                                         // the next pane
api.panes.root;                                           // the tree, reactive: panes and splits
api.panes.focused;                                        // { id, tabs, active }
```

The layout is saved with the tabs, and comes back at the next launch.

### Styling panes

The panes only lay out: style them with these attributes, or `class` on `content`:

```css
[data-sd-pane] { background: var(--surface); border-radius: 8px; }
[data-sd-pane][data-focused] { box-shadow: 0 0 0 1px var(--accent); }
:root {
	--sd-pane-gap: 6px;                     /* the room between panes, where the line is grabbed */
	--sd-pane-splitter: transparent;        /* the line, at rest */
	--sd-pane-splitter-hover: #5f62ef80;    /* under the pointer, or with the keyboard's focus */
	--sd-pane-splitter-active: #5f62ef;     /* being dragged */
	--sd-pane-drop: #5f62ef59;              /* where a dragged tab will land */
}
```

| Attribute | On |
| --- | --- |
| `[data-sd-panes]` | All the panes |
| `[data-sd-pane]`, with `[data-focused]`, `[data-top]`, `[data-right]`, `[data-bottom]`, `[data-left]` (the sides of the panes it touches) | A pane |
| `[data-sd-pane-body]` | Where its tab's view goes: give it a background for while a page loads |
| `[data-sd-splitter]` (`row` or `column`), with `[data-dragging]` | The line between two panes |
| `[data-sd-pane-drop]` | Where a dragged tab will land |
| `[data-sd-tab-ghost]` | The tab following the pointer |
| `html[data-sd-pane-dragging]`, `html[data-sd-pane-resizing]` | While dragging, while resizing |

### Limits

- A web view is drawn over the page. A dialog or menu from your window's page can't cover a pane, and the tab following the pointer shows over the bars and between panes, not over a web view. The zone it would land in does show, since the view makes room for it.
- Each tab is a web process, about 40 MB and more with its page. Compare with [`maxViews`](#the-windows-tabs) and `prewarm` (a tab opens without starting a process).
- A tab dragged out of the window opens in a new window with its page starting again, and it can't join another window's panes.
- The line between two panes can only be grabbed in the gap between them, `--sd-pane-gap`: a web view takes every press on it, so the page can't reach over a pane. A gap under about 4px is hard to grab.
- When the window is too small for every pane at `minPaneSize`, panes keep their proportions and go under it. The system slows the timers of a tab not on screen.
- `split` is set once, at start. The window's own route isn't rendered: its server `load` still runs at launch, so keep the root route light.

## Styling

The bar only lays out (zero-specificity styles): style it with `class` and the state attributes.

| Selector | |
| --- | --- |
| `[role=tablist]` (`data-sd-tabbar`) | The bar; its `gap` spaces the tabs |
| `[role=tab]`, `[data-active]`, `[data-pinned]`, `[data-suspended]`, `[data-dragging]` | A tab and its states (`data-suspended`: its view closed to free memory) |
| `[data-sd-tab-drop]` | The line where a dragged tab lands (`--sd-tab-drop-color`, default `Highlight`) |
| `[data-sd-tab-title]`, `[data-sd-tab-close]` | The default content |
| `[data-sd-tab-new]` | The + button |

The drag is native drag and drop ([pragmatic-drag-and-drop](https://atlassian.design/components/pragmatic-drag-and-drop/)): the system's drag image follows the pointer, beside it, out of the window and over other windows. The [dashboard example](https://github.com/beynar/svelte-desktop/tree/main/examples/dashboard) has the window's tabs, with a kept-alive `/activity`.
