The main window is described by `window` in `desktop.config.ts` and controlled at run time through `host.window`.

```ts desktop.config.ts
window: { width: 960, height: 680, minWidth: 520, minHeight: 400, autosaveName: 'main', titleBarStyle: 'hiddenInset' },
```

`window: false` is the same as `window: { visible: false }` without waiting for the page (`hiddenUntilReady` off): the main window is created hidden, for [menu-bar apps](/ui/menu-bar-and-popovers). It still loads your app and can be shown with `host.window.show()`.

`quitOnLastWindowClosed` is a top-level key of `desktop.config.ts`, not part of `window`. It defaults to `true`. Set it to `false` to hide the last visible window instead of quitting: its page keeps its state, background work and push connections go on, and a Dock click, a notification click or a second launch shows it again.

## At run time

```svelte
<h1>{host.window.title}</h1>
{#if host.window.fullscreen}<p>Full screen</p>{/if}
<button onclick={() => host.window.toggleMaximize()}>Maximize</button>
<button onclick={() => host.window.setTitle('Untitled')}>Rename</button>
```

`host.window` exposes reactive state (`title`, `focused`, `maximized`, `fullscreen`, `bounds`, `size`, `position`, `state`, `scaleFactor`) and window operations. Use `host.windows` when targeting another window by id; the reactive `host.window` wrappers act on the calling window.

The operations cover geometry (`setSize`, `setBounds`, `center`, `positionTo`), state (`minimize`, `maximize`, `show`, `hide`, `focus`, `close`), full screen, window chrome (`setTitleBarStyle`, `setOpacity`, `setTheme`, `setVibrancy`), behavior (`setAlwaysOnTop`, `setIgnoresMouseEvents`, `setContentProtected`) and macOS extras such as `setDocumentEdited`, which shows the dot in the close button. The [window reference](/host/windows/window) lists them all.

## Title bar styles

| `titleBarStyle` | macOS |
| --- | --- |
| `default` | The normal title bar. |
| `transparent` | The page extends under the title bar; the title stays. |
| `hidden` | The page extends under the title bar; traffic lights at the corner. |
| `hiddenInset` | Same, with the traffic lights inset. |

Your header takes the title bar's place. The shell sets CSS variables and attributes so it can line up with the window controls:

```css src/app.css
header {
  --app-region: drag;                                          /* or the data-desktop-drag attribute */
  min-height: max(var(--desktop-titlebar-height, 0px), 2.5rem);
  padding-left: max(var(--desktop-controls-width, 0px), 1rem); /* clear the traffic lights */
}
.search { --app-region: no-drag; }  /* carve out a region; links, buttons and inputs stay clickable anyway */
```

| Set by the shell | |
| --- | --- |
| `--desktop-titlebar-height` | Height of the title bar strip; `0` in full screen |
| `--desktop-controls-width` | Width taken by the window controls; `0` in full screen |
| `html[data-desktop-titlebar]` | Present with a hidden title bar; `fullscreen` while in full screen |
| `html[data-desktop-controls]` | `native` (macOS keeps its buttons) or `none` (the page draws its own) |

- **Drag regions.** Any element with `--app-region: drag` or the `data-desktop-drag` attribute drags the window. Double-click follows the system setting (zoom or minimize).
- **The title bar strip behaves like a title bar.** It drags the window whatever the page puts there (controls stay clickable; `--app-region: no-drag` opts an element out). Scrolling over it doesn't scroll the page, so title-bar gesture tools such as Swish keep working. A gesture is routed as a whole by where it began: one started in the page keeps scrolling.
- **Switch at run time** with `host.window.setTitleBarStyle(style)`.

### Linux and Windows

A hidden title bar there is a frameless window: there are no native buttons to keep, so `html[data-desktop-controls="none"]` tells the page to draw its own. Drag regions and double-click to maximize work the same.

```css
.window-buttons { display: none; }
:root[data-desktop-controls="none"] .window-buttons { display: flex; }
```

```svelte
<div class="window-buttons">
  <button onclick={() => host.window.minimize()}>–</button>
  <button onclick={() => host.window.toggleMaximize()}>□</button>
  <button onclick={() => host.window.close()}>×</button>
</div>
```

## Vibrancy and Liquid Glass

macOS draws translucent materials behind an app's content, as in Finder's sidebar or the Music app. On macOS 26 it also draws Liquid Glass, the glass of its own controls, with refraction and highlights. The system draws them behind the web view, so they cost the page nothing, unlike a CSS `backdrop-filter`. They blur what's behind the *window* (the desktop, other windows), not the page's own content.

### In CSS

Declare a material on an element. The shell draws it behind that element, at its size and with its `border-radius`, and follows it as it moves, resizes, appears and disappears:

```css
.sidebar  { --desktop-material: sidebar; }
.toolbar  { --desktop-material: glass; --desktop-material-tint: var(--color-primary); }
.overlay  { --desktop-material: hud; --desktop-material-state: active; border-radius: 12px; }

@media (prefers-color-scheme: dark) { .panel { --desktop-material: glass-clear; } }
```

| Property | Values |
| --- | --- |
| `--desktop-material` | `sidebar`, `titlebar`, `header`, `content`, `window`, `underWindow`, `underPage`, `menu`, `popover`, `sheet`, `hud`, `tooltip`, `fullscreenUI`, `selection`; `glass` or `glass-clear` for Liquid Glass (macOS 26; `underWindow` before); `none` |
| `--desktop-material-tint` | Any CSS color: the glass's tint, its alpha the strength (`color-mix(in oklab, var(--color-primary) 30%, transparent)`) |
| `--desktop-material-state` | `active` keeps a vibrancy material vivid while the window is inactive; `inactive` always dims it. By default it dims with the window, like the system's own. |

The attribute `data-desktop-material="sidebar"` does the same. The properties are not inherited: only the element that declares one gets the material, not its children.

**The element must not paint a background, and neither may what's under it in the page.** The material is behind the page, so any background above it covers it: the element's own, and its ancestors' up to `html`. Where the shell draws materials, `html` has the `data-desktop-materials` attribute. Use it to drop those backgrounds in the app and keep them in a browser, on Linux and on Windows:

```css
html[data-desktop-materials],
html[data-desktop-materials] body,
html[data-desktop-materials] .sidebar { background: transparent; }
main { background: var(--surface); } /* opaque where you want it */
```

An element whose material is drawn right now has `data-desktop-material-on`. A material has no strength setting: to show less of it, give the element a partly transparent background (`color-mix(in oklab, var(--surface) 40%, transparent)` shows 60% of it).

Glass shows what's behind the window, so while an element has glass, the window is non-opaque: where the page paints nothing at all, the desktop shows through. Vibrancy needs nothing of the kind.

Materials are drawn behind the window's page only, not behind a kept-alive tab's own web view ([`<WindowTabs>`](/ui/tabs) `keepAlive`). They follow elements on each frame they move; during a live window resize, they can lag a frame behind. An element clipped by a scrolling parent gets its material at its full box, within the window.

### The whole window

For the whole window instead, behind every transparent part of the page:

```ts desktop.config.ts
window: { titleBarStyle: 'hiddenInset', vibrancy: 'sidebar' },
```

Change it at run time with `host.window.setVibrancy('hud')` (`{ state: 'active' }` keeps it vivid while the window is inactive), or remove it with `setVibrancy(null)`. On macOS 26, `host.window.setGlass()` puts Liquid Glass there instead:

```ts
await host.window.setGlass({ style: 'regular' });                 // frosted, readable over anything
await host.window.setGlass({ style: 'clear', tint: '#5f62ef40' }); // more transparent, tinted
await host.window.setGlass(null);                                  // back to an opaque window
```

`tint` is `#rgb`, `#rrggbb` or `#rrggbbaa`. `cornerRadius` rounds the glass, in points. A window has one of these at a time: `setGlass` removes vibrancy, and `setVibrancy` removes glass. Before macOS 26, `setGlass` uses the `underWindow` material and resolves `{ glass: false }`. Materials declared in CSS can be used along with them.

### Light and dark

Materials are light or dark with the window's appearance, which follows the system, not your page. If the page can be light while the system is dark (a theme picker), give the window the page's theme, or a light page sits on a dark material:

```ts
const dark = getComputedStyle(document.documentElement).colorScheme.includes('dark');
await host.window.setTheme(dark ? 'dark' : 'light'); // 'system' to go back
```

macOS only: elsewhere, `--desktop-material` is ignored and `html` has no `data-desktop-materials`.

## Traffic lights

With a hidden title bar and a taller toolbar of your own, place the traffic lights where it wants them (macOS): `{ x, y }` is the close button's top-left corner, in points from the window's top-left.

```ts desktop.config.ts
window: { titleBarStyle: 'hidden', trafficLightPosition: { x: 18, y: 18 } },
```

Their custom placement is reapplied after resizing, focus changes and leaving full screen; macOS controls their presentation during full screen. `--desktop-titlebar-height` grows to reach below them, and `--desktop-controls-width` follows. At run time, call `host.window.setTrafficLightPosition({ x: 20, y: 24 })`, or pass `null` to put them back.

## Running out of sight

On macOS, WebKit can slow a page down when its window is covered or minimized. A player or a live dashboard may need to keep going:

```ts desktop.config.ts
window: { backgroundThrottling: false },
```

At run time, use `host.webview.setBackgroundThrottling(false)`. For an embedded view, pass `backgroundThrottling: false` to `host.view.create` along with its route and bounds.

Disabling throttling costs energy and does not guarantee a timer rate; macOS can still throttle minimized windows. This option and `setBackgroundThrottling` are macOS-only. Put long-running work in [background jobs](/native/jobs) or [services](/native/services), where it does not depend on page timers.

## No elastic overscroll

On desktop, the bridge sets `:where(html, body) { overscroll-behavior: none }`, with zero specificity, so the page doesn't rubber-band. Bring it back with `html { overscroll-behavior: auto }`, or set it per scroll container.

## Multiple windows

```ts
const { windowId } = await host.windows.create({ path: '/inspector', title: 'Inspector', width: 520, height: 420, animate: true });
await host.windows.setTitle('Inspector (2)', windowId);
host.windows.onClosed(({ windowId }) => console.log('closed', windowId));
```

Window-targeted operations on `host.windows` take an optional trailing `windowId`; without it they target the calling page's window (the main window from server code). `0` is the main window. `host.windows.list()` returns `{ windowId, label, focused, visible, bounds }` rows, `host.windows.getInfo()` the calling window's own row, and `host.windows.get(label)` finds one.

Common options: `label` (unique per app, so you can find the window with `host.windows.get(label)`), `path` (the app route, default `"/"`) or `url` (another origin gets no native bridge), `title`, `x`, `y`, `width`, `height`, `decorations: false` for a borderless window, `transparent`, `alwaysOnTop`, `visible` and `focus`. On macOS also `animate` (see [Animation](#animation)) and `parentId`, `modal`, `type` and `focusable` (see [Parents, modal children and panels](#parents-modal-children-and-panels-macos)). The full list, with defaults, is in the [`create` reference](/host/windows/windows#createoptions).

Windows emit events such as `onCreated`, `onClosed` and `onBoundsChanged`. Use [`host.broadcast`](/host/data/events#broadcast-between-contexts) to message between windows.

### Parents, modal children and panels (macOS)

```ts
const parent = await host.windows.getInfo();
const child = await host.windows.create({
  parentId: parent.windowId, type: 'panel', focusable: false,
  title: 'Inspector', path: '/inspector', width: 320, height: 420,
});
const modal = await host.windows.create({
  parentId: parent.windowId, modal: true, path: '/confirm', width: 420, height: 260,
});
await host.windows.close(modal.windowId);
await host.windows.setParent(null, child.windowId); // detach the panel
```

A normal child uses AppKit's child-window relationship: moving the parent moves its children. `modal: true` requires a valid parent and presents a native sheet, which blocks interaction with that parent until closed or hidden. It uses the same AppKit sheet mechanism as `host.dialog.sheet`; use that route-dialog API when you need its result contract. A second attached modal is rejected. Hide a modal before changing its parent, then show it on the new parent. Modal children must remain focusable and cannot be detached; close one and create an independent window instead.

`type: 'normal'` is the default. `type: 'panel'` creates an `NSPanel`, which can become key when `focusable: true` but does not become the application's main document window. `focusable: false` prevents key focus, including during creation. `setFocusable(bool, windowId)` changes that policy at runtime; `isFocusable(windowId)` reads it. `focus: false` shows a window without requesting key focus.

Normal windows own native full-screen Spaces; panels and modal children are auxiliary windows and reject requests to own a full-screen Space. `focus()` rejects `unavailable` for nonfocusable windows. macOS controls application activation: a refused request resolves `{ activated: false }`, and a successful one does not guarantee that another foreground app will yield focus.

`getParent(windowId)` returns a parent info row or `null`; `getChildren(windowId)` returns direct child info rows. On macOS, info rows also expose `parentId`, `modal`, `sheetAttached`, `type`, and `focusable`; `sheetAttached` observes whether AppKit has actually presented the sheet. `setParent(parentId, windowId)` reparents a child and rejects missing parents and cycles. Closing a parent also closes its descendants. Relationship options, panel policy and these getters are macOS-only; other backends return `unsupported` for the new operations.

### Window transitions (macOS)

```ts
const off = host.windows.on('fullscreenChanged', ({ windowId, fullscreen, transition }) => {
  // transition: 'entered' | 'exited'; macOS has finished the Spaces transition.
  console.log(windowId, fullscreen, transition);
});
```

`host.windows.on(name, callback)` supports `shown`, `hidden`, `minimized`, `restored`, `fullscreenChanged`, `moved`, `resized`, `focus` and `blur`. Every payload carries `windowId`; `moved` and `resized` also carry the outer frame `{ x, y, width, height }` in screen points with a top-left origin. Geometry events stream after each native change. Full-screen events come from AppKit's completed-transition notifications, not the setter's early reply. `restored` means deminiaturized. Visibility events track ordering, alpha, and application hide/unhide; merely covering a window does not hide it.

Named helpers are also available: `onShown`, `onHidden`, `onMinimized`, `onRestored`, `onFullscreenChanged`, `onMoved`, `onResized`, `onFocus`, `onBlur`. They return unsubscribe functions. Existing `focusChanged` and `boundsChanged` events remain, and `host.window.fullscreen` refreshes after full-screen completion.

Read window policy with `getLevel()` (numeric AppKit level), `isAlwaysOnTop()`, `hasShadow()`, `isMovable()`, `getMinSize()` and `getMaxSize()`. Size limits use **content points**, matching `setMinSize` / `setMaxSize`; a maximum axis of `0` means unconstrained. Every getter accepts a trailing `windowId`, as do the existing setters.

For an app-wide unsaved-work guard, see [Cancellable quit](/host/app/app#cancellable-quit-macos). The close veto below handles individual window closes.

## Animation

A window can come in animated each time it shows — at launch, `windows.create`, `window.show()`: `animate: true` fades it in while it slides down 10 points into place, in 180 ms. Or describe your own:

```ts
host.windows.create({
	path: '/inspector',
	animate: { duration: 260, easing: [0.2, 0.9, 0.1, 1], offset: { x: 0, y: 24 }, scale: 0.96, opacity: 0 },
});
```

## Confirm before closing

Arm the close veto: the red button and the native Close menu action then emit `willClose` instead of closing. With `<WindowTabs>`, Cmd+W closes a tab; use its `beforeClose` prop for that guard.

```ts
const current = await host.windows.getInfo();
const off = host.windows.onWillClose(async ({ windowId }) => {
  if (windowId !== current.windowId) return;
  const { response } = await host.dialog.showMessageBox({
    type: 'warning', message: 'Discard unsaved changes?', buttons: ['Discard', 'Cancel'],
  });
  if (response === 0) {
    await host.windows.setCloseVeto(false, current.windowId);
    off();
    await host.windows.close(current.windowId);
  }
});
await host.windows.setCloseVeto(true, current.windowId);
```

Programmatic `host.windows.close()` bypasses the veto. For a single-window app, `host.window.onCloseRequested(handler)` subscribes and arms it together, returning an async cleanup function that disarms and unsubscribes.

## Saving the frame

`autosaveName` persists the main window's frame natively. For more control, `host.windowState` writes a JSON snapshot (`window-state.json` in the app's data directory). It uses Bun's file API in the app server; page code can call it too, through the server:

```ts
await host.windowState.save({ flags: ['size', 'position', 'maximized'] });
await host.windowState.restore(); // applies what the snapshot captured
```

Flags: `size`, `position`, `maximized`, `visible`, `fullscreen` (default: all). The JSON snapshot is shared, not one file per window. Its `visible` flag records whether the window is minimized, not whether it was explicitly hidden. It captures outer-frame bounds but restores size with the content-size setter, so decorated windows can restore to a different outer size. Prefer `autosaveName` for native main-window frame persistence. See [window state](/host/windows/window-state) for the restore rules.
