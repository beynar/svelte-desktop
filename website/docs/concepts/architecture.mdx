---
title: Architecture
description: How one Bun executable runs the native UI, the SvelteKit server, and the bridge between the page and the OS.
---

A built app is one `bun --compile` executable plus the native shell library and any app plugins, addons and sidecars. The app process has two main JavaScript threads and a small third one that watches the server; the web view also uses the system engine's helper processes. On macOS, the bundle looks like this:

```txt
App.app/Contents/MacOS/App                       one bun --compile executable (UI thread + Worker)
App.app/Contents/Frameworks/libshell.dylib       web view + native services
                           libapp-native.dylib  Swift / Objective-C / C / C++ plugin
                           plugins/*.dylib      Rust / Go plugins
                           addons/*.node        Node-API addons

main thread: Cocoa run loop (WKWebView)   <->   Worker: Bun.serve (SvelteKit) + desktop API
             one native dispatcher for the page bridge, FFI and plugins
```

## The threads

- **UI thread.** Bun's main thread becomes the native UI thread (Cocoa on macOS, GTK on Linux, Win32 on Windows). It creates the window and loads native plugins before entering the run loop. While that loop runs, Bun's main-thread JavaScript event loop is blocked, so put your app code in the Worker (server code) or the page, never on the main thread. Page JavaScript runs in the web engine, separately from Bun.
- **Worker.** A Bun Worker runs `Bun.serve` with the SvelteKit handler and the server-side desktop API. Load functions, remote functions, hooks and endpoints all run here, with full Bun APIs.
- **Supervisor.** A second, very small Worker, parent of the first, runs no app code. It's there because the UI thread can't see the server die: its event loop is blocked. It costs a few MB of memory. See [When something crashes](#when-something-crashes).

Native plugins share the app process, but their command handlers need not run on the UI thread: Node-API addons run in the server's Bun runtime; persistent services, background jobs and sidecars run in child processes. On macOS, plugin replies and events are marshaled back to the UI thread, so a blocked UI thread delays results that finished elsewhere. Jobs, services and sidecars are started by the server and talk to it over Bun IPC or their own streams; they have no `host` global. See [Threads and processes](/native/threads) to choose where code runs, and [Native code](/native) to choose an approach.

Quitting runs the Worker's `host.onBeforeQuit` hooks, then writes what [`host.store`](/host/data/store) still has pending (waiting at most a second), then stops jobs and services (sidecars are yours to stop). On macOS this happens during AppKit's asynchronous quit phase; backends that return from the run loop perform cleanup afterward, with a default 3-second shutdown wait. Shutdown force-closes server sockets rather than waiting for every request to finish. Closing the last window keeps the app running when `quitOnLastWindowClosed` is `false`.

## When something crashes

**The server.** An error thrown out of server code, an exception while its modules load, a failed start or a `process.exit()` with another code than 0 end the Worker. The supervisor writes the reason to `app.log` and to the next [`host.crashInfo()`](/host/data/server#crashinfo), then starts the app again as a new process: at once, then after 1 and 3 seconds. After three restarts in five minutes it stops, shows a message naming the log file, and quits; the next launch starts counting again.

The whole process restarts, not just the Worker, so nothing has to be carried over: a new secret and session cookie, the same port, a new event sink, and none of the tray icons, windows or quit handlers the dead server had asked for. The window closes and opens again, what's unsaved in its pages is lost, and only what the app opens at launch comes back. A restart counts as a launch for an [update](/shipping/self-update) waiting to be confirmed, so a version whose server dies before that rolls back.

These don't restart anything:

- A **rejected promise** nothing handles is logged, and the server carries on. Its state is intact, and a background request failing while offline shouldn't reload the window.
- `process.exit(0)` in server code quits the app, without running `host.onBeforeQuit` hooks.
- A server stuck in an **endless loop** isn't detected: telling it from long synchronous work needs a guess, and a wrong one would kill a working app.
- A crash in **native code** takes the process down at once. The next launch reports it as an unclean exit, and nothing restarts it.

**The web process.** A view whose web process dies reloads after 0.1, 1 and then 4 seconds. A fourth crash within five minutes stops that: an app page is replaced by a page saying so, with a link to try again, and `webcontent-terminated` arrives with `gaveUp: true`. A view showing another site stays blank. On macOS, a view with `recovery: 'manual'` is left to you.

On Windows, a page that's only unresponsive isn't reloaded: it's often just busy, and a reload would lose what's typed in it. The user is asked whether to wait or reload, and `webcontent-unresponsive` arrives on the server. If the WebView2 browser process itself keeps dying, the app says so and quits, since no page is left to say it.

## The localhost session

The server listens on a loopback port that comes from the app's identifier. It stays the same across launches, because web views keep `localStorage` and IndexedDB per origin, port included. If it's taken, the app uses another one for that launch, and doesn't see what's stored on the usual one. A gate in front of SvelteKit keeps other local processes and web pages out:

1. **Host check** against DNS rebinding.
2. **One-time secret.** The UI thread generates it and the window's first navigation trades it for an `HttpOnly`, `SameSite=Strict` session cookie. Both are new in each process, so after a [crash restart](#when-something-crashes) too. App requests without the cookie get a 403. Immutable build routes (including prerendered pages) bypass the cookie gate, as do single-use OAuth callback URLs.
3. **Cookies that work on http.** SvelteKit marks cookies `Secure` in production; WebKit drops those on `http://127.0.0.1`, so the gate removes `Secure` and changes `SameSite=None` to `Lax` (the origin is the loopback). It also disables Bun's idle timeout for slow requests.

## The bridge

Native features are ops (`window.setTitle`, `clipboard.readText`, ...) handled by one native dispatcher, reached two ways:

| Caller | Path |
| --- | --- |
| Page code | Straight to native through an origin-checked message handler (only the app origin's main frame is answered). |
| Server code | Over FFI to the same dispatcher (over an RPC bridge in `vite dev`). |

Both use the same op names, arguments and error codes, which is why [`host`](/host) is the same object in both places. Pages can be restricted to a list of ops with [`bridge.allow`](/reference/config); server code is never restricted.

Messages flow the other way too: native events (theme changes, menu clicks, notification responses) reach every page and server code, and `host.broadcast(channel, data)` sends to every window, popover and the server.

## Dev mode

`vite dev` starts the dev shell as a child process: the same native window, pointed at the Vite server. HMR and the Web Inspector work in the window; server code runs in the Vite process and reaches native APIs through a token-protected WebSocket bridge to the shell's Worker. That Worker handles the bridge, not SvelteKit. On macOS, a configured app icon replaces Bun's in the Dock.

## Built in

- **Logs.** With no terminal (started from Finder, a launcher or Explorer), the app logs to `~/Library/Logs/<identifier>/app.log` on macOS (other platforms use the app's log directory). The file rotates at 5 MB. `KITOP_LOG=stdout` or `file` forces either destination; a server crash goes to the file either way.
- **Graceful quit** on signals, Cmd+Q and Dock Quit, with `host.onBeforeQuit(fn)` in server code.
- **Crash recovery.** A bounded number of restarts for the server and reloads for the page; see [When something crashes](#when-something-crashes). `host.crashInfo()` reports an unclean previous exit, the error that ended the server, and OS crash reports written since that launch (macOS and Windows; no OS report collection on Linux).
- **Single instance.** On Linux and Windows a second launch hands its arguments (documents, links) to the running app; macOS does this natively.
- **No `.env` or `bunfig.toml` pickup** at runtime: the app doesn't change behavior based on the directory it's launched from.
