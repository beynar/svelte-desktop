---
title: Architecture
description: How one Bun executable runs the native UI, the SvelteKit server, and the bridge between the page and the OS.
---

A built app is one `bun --compile` executable plus the native shell library and any app plugins, addons and sidecars. The app process has two main JavaScript threads; the web view also uses the system engine's helper processes. On macOS, the bundle looks like this:

```txt
App.app/Contents/MacOS/App                       one bun --compile executable (UI thread + Worker)
App.app/Contents/Frameworks/libshell.dylib       web view + native services
                           libapp-native.dylib  Swift / Objective-C / C / C++ plugin
                           plugins/*.dylib      Rust / Go plugins
                           addons/*.node        Node-API addons

main thread: Cocoa run loop (WKWebView)   <->   Worker: Bun.serve (SvelteKit) + desktop API
             one native dispatcher for the page bridge, FFI and plugins
```

## The two threads

- **UI thread.** Bun's main thread becomes the native UI thread (Cocoa on macOS, GTK on Linux, Win32 on Windows). It creates the window and loads native plugins before entering the run loop. While that loop runs, Bun's main-thread JavaScript event loop is blocked. Page JavaScript runs in the web engine, separately from Bun.
- **Worker.** A Bun Worker runs `Bun.serve` with the SvelteKit handler and the server-side desktop API. Load functions, remote functions, hooks and endpoints all run here, with full Bun APIs.

Native plugins share the app process, but their command handlers need not run on the UI thread: Swift handlers use `MainActor`, Rust handlers use new threads, and Go handlers use goroutines. Node-API addons run in the server's Bun runtime; persistent services, background jobs and sidecars run in child processes. See [Threads and processes](/native/threads) for execution and communication details, and [Native code](/native) to choose an approach.

Quitting runs the Worker's `host.onBeforeQuit` hooks. On macOS this happens during AppKit's asynchronous quit phase; backends that return from the run loop perform cleanup afterward, with a default 3-second shutdown wait. Shutdown force-closes server sockets rather than waiting for every request to finish. Closing the last window keeps the app running when `quitOnLastWindowClosed` is `false`.

## The localhost session

The server listens on a random loopback port. A gate in front of SvelteKit keeps other local processes and web pages out:

1. **Host check** against DNS rebinding.
2. **One-time secret.** The UI thread generates it and the window's first navigation trades it for an `HttpOnly`, `SameSite=Strict` session cookie. App requests without the cookie get a 403. Immutable build routes (including prerendered pages) bypass the cookie gate, as do single-use OAuth callback URLs.
3. **Cookies that work on http.** SvelteKit marks cookies `Secure` in production; WebKit drops those on `http://127.0.0.1`, so the gate removes `Secure` and changes `SameSite=None` to `Lax` (the origin is the loopback). It also disables Bun's idle timeout for slow requests.

## The bridge

Native features are ops (`window.setTitle`, `clipboard.readText`, ...) handled by one native dispatcher, reached two ways:

| Caller | Path |
| --- | --- |
| Page code | Straight to native through an origin-checked message handler (only the app origin's main frame is answered). |
| Server code | Over FFI to the same dispatcher (over an RPC bridge in `vite dev`). |

Both use the same op names, arguments and error codes, which is why [`host`](/host) is the same object in both places. Pages can be restricted to a list of ops with [`bridge.allow`](/reference/config); server code is never restricted.

Messages flow the other way too: native events (theme changes, menu clicks, notification responses) reach every page and server code, and `host.broadcast(channel, data)` sends to every window, popover and the server.

## Dev mode

`vite dev` starts the dev shell as a child process: the same native window, pointed at the Vite server. HMR and the Web Inspector work in the window; server code runs in the Vite process and reaches native APIs through a token-protected WebSocket bridge to the shell's Worker. That Worker handles the bridge, not SvelteKit. On macOS, a configured app icon replaces Bun's in the Dock.

## Built in

- **Logs.** Launched from Finder, both threads log to `~/Library/Logs/<identifier>/app.log`.
- **Graceful quit** on signals, Cmd+Q and Dock Quit, with `host.onBeforeQuit(fn)` in server code.
- **Crash recovery.** If the web content process dies, the page reloads by default; web views can opt into manual recovery. `host.crashInfo()` reports an unclean previous exit and OS crash reports written since that launch (macOS and Windows; no OS report collection on Linux).
- **Single instance.** On Linux and Windows a second launch hands its arguments (documents, links) to the running app; macOS does this natively.
- **No `.env` or `bunfig.toml` pickup** at runtime: the app doesn't change behavior based on the directory it's launched from.
