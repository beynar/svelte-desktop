---
title: Adopting an existing app
description: What init changes in a SvelteKit project, and what behaves differently once it runs on a loopback server inside a desktop app.
---

Your routes, load functions, remote functions, hooks and endpoints run as they are, on Bun. The differences come from where they now run. To do the conversion, follow [Convert a SvelteKit app](/convert-sveltekit-app); this page is what's behind it.

## What `init` does

```sh
bun add -d @kitop/shell @sveltejs/adapter-bun@1.0.0-next.2 @types/bun
bunx kitop init
bun run dev --mac   # or --windows, --linux; with no flag, the website
```

The adapter's version is not a suggestion: see [what an app needs](/reference/versioning#what-an-app-needs).

- Writes `desktop.config.ts`, with the app name taken from `package.json` and the identifier `com.example.<name>`. **Change the identifier** before you ship. An existing config is left alone.
- In `vite.config.ts` (or `.js`), replaces the `sveltekit` import and calls with `desktop`. Your options stay, and with an `adapter` among them the project stays a website: that adapter builds it unless a desktop target is asked for. If it finds no `sveltekit(` call, it tells you to add `desktop()` yourself.
- Sets `dev` and `build` to `kitop dev` and `kitop build`, and adds `test:desktop`, replacing existing ones of those names, and adds `.desktop` to `.gitignore`. `package.json` keeps its formatting.
- Writes a first test, `tests/app.test.ts`, if there's no `tests` folder.

It does not change `svelte.config.js`. If you configure the adapter there, it tells you, and you move it by hand. A desktop target uses the shell's own adapter, a wrapper around `adapter-bun`, so keep `@sveltejs/adapter-bun` installed, at that version. `kit.paths.origin` is ignored: the app runs on a loopback port of its own.

## What to check

- **Adapter.** In the desktop app, what your adapter does (static hosting, edge or Node output) doesn't apply. That build produces an app bundle, and your adapter builds the website.
- **Runtime.** Server code runs on Bun, not Node. Node-only modules that Bun doesn't support won't work, and code that checks for a Node runtime may branch differently. For a desktop target, `vite` itself must run through Bun, which `kitop dev` and `kitop build` do. The website's build can run on Node.
- **`$env`.** There is no `.env` or `bunfig.toml` pickup at runtime ([Architecture](/concepts/architecture#built-in)), so values read by `$env/dynamic/*` must come from the environment the app is launched with, which for a desktop app is usually nothing. `$env/static/*` values are read when you build and end up in the bundle. Don't ship secrets inside the app; anything in the bundle can be read.
- **Cookies and sessions.** Cookies are set on `http://127.0.0.1`. The gate removes `Secure` and turns `SameSite=None` into `Lax` so the web view keeps them. A cookie-based login still works, but there is no `Secure` flag to rely on.
- **External services.** Requests from the page to another origin are subject to that service's CORS rules, with the app's loopback origin as `Origin`. Allow-lists naming your production domain won't match. Calls from server code aren't subject to CORS. OAuth needs the [loopback or scheme flow](/host/web/oauth).
- **Prerendered pages** are embedded in the executable and served without the session cookie.
- **Platform support** varies; see [Limitations](/shipping/limitations).

Then add the `host` API where it helps. In a browser tab `host.available` is `false` and calls reject, so guard shared code with it.
