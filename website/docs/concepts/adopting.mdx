---
title: Adopting an existing app
description: What init changes in a SvelteKit project, and what behaves differently once it runs on a loopback server inside a desktop app.
---

Your routes, load functions, remote functions, hooks and endpoints run as they are, on Bun. The differences come from where they now run.

## What `init` does

```sh
bunx svelte-desktop init
bun add -d @sveltejs/adapter-bun @svelte-desktop/shell
bun run dev
```

- Writes `desktop.config.ts`, with the app name taken from `package.json` and the identifier `com.example.<name>`. **Change the identifier** before you ship. An existing config is left alone.
- In `vite.config.ts` (or `.js`), replaces the `sveltekit` import and calls with `desktop`, and removes the `adapter: adapter(...)` option and the `import adapter` line. If it finds no `sveltekit(` call, it tells you to add `desktop()` yourself.
- Sets the `dev`, `build` and `test:desktop` scripts, replacing existing ones of those names, and adds `.desktop` to `.gitignore`.

It does not change `svelte.config.js`. If you configure the adapter there, it tells you, and you remove it by hand. The desktop plugin sets its own adapter, a wrapper around `adapter-bun`, so keep `@sveltejs/adapter-bun` installed. `kit.paths.origin` is ignored: the app runs on a random loopback port.

## What to check

- **Adapter.** Anything the old adapter did (static hosting, edge or Node output) no longer applies. The build produces an app bundle.
- **Runtime.** Server code runs on Bun, not Node. Node-only modules that Bun doesn't support won't work, and code that checks for a Node runtime may branch differently. `vite` itself must run through Bun: `bunx --bun vite`.
- **`$env`.** There is no `.env` or `bunfig.toml` pickup at runtime ([Architecture](/concepts/architecture#built-in)), so values read by `$env/dynamic/*` must come from the environment the app is launched with, which for a desktop app is usually nothing. `$env/static/*` values are read when you build and end up in the bundle. Don't ship secrets inside the app; anything in the bundle can be read.
- **Cookies and sessions.** Cookies are set on `http://127.0.0.1`. The gate removes `Secure` and turns `SameSite=None` into `Lax` so the web view keeps them. A cookie-based login still works, but there is no `Secure` flag to rely on.
- **External services.** Requests from the page to another origin are subject to that service's CORS rules, with the app's loopback origin as `Origin`. Allow-lists naming your production domain won't match. Calls from server code aren't subject to CORS. OAuth needs the [loopback or scheme flow](/host/web/oauth).
- **Prerendered pages** are embedded in the executable and served without the session cookie.
- **Platform support** varies; see [Limitations](/shipping/limitations).

Then add the `host` API where it helps. In a browser tab `host.available` is `false` and calls reject, so guard shared code with it.
