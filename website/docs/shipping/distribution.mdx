`bunx --bun vite build` compiles the server into one executable and packages it for the target. Output goes to `.desktop/dist` (`build.outDir`). The target is the host OS unless `build.target` (`macos`, `linux` or `windows`) or `KITOP_TARGET` says otherwise; Linux and Windows can be built from macOS. The environment variables override the config. Building macOS requires macOS and its Apple toolchain.

```sh
bunx --bun vite build                               # macOS, the host
KITOP_TARGET=linux bunx --bun vite build   # cross-build
KITOP_TARGET=windows KITOP_TARGET_ARCH=arm64 bunx --bun vite build
```

## macOS

```sh
CODESIGN_IDENTITY="Developer ID Application: You (TEAMID)" NOTARY_PROFILE=notary bunx --bun vite build
```

| Output | |
| --- | --- |
| `<App>.app` | One executable, `libshell.dylib`, C/C++/Swift/Objective-C and Rust/Go plugins, addons and sidecars; `Info.plist` from the config |
| `<Exe>-<version>-darwin-<arch>.zip` | `build.zip: false` to skip |
| `<Exe>-<version>-darwin-<arch>.dmg` | With an Applications link; `build.dmg: false` to skip |
| `release/` | Update archives and a manifest when [`update`](/shipping/self-update) is set; unsigned without a private key |

The pipeline:

1. **Info.plist** from the config: `identifier`, `version`, URL `schemes`, document types (`fileTypes`), usage strings (`permissions`), `LSUIElement` (`trayOnly`), `build.minimumSystemVersion` (default `12.0`) and any extra `plist` keys.
2. **Signing.** Nested code first, then the bundle, with the hardened runtime and the entitlements Bun's JIT needs, plus device entitlements derived from `permissions`. `sign.entitlements` adds more; `sign.provisioningProfile` embeds a profile (needed for APNs).
3. **Notarization.** When an identity and a notary profile are set, a local pre-flight runs, then the app and the DMG are submitted with `notarytool` and stapled.

Bundled sidecars and addons are nested code. On macOS each sidecar is signed before the app with the app's identity and the hardened runtime, but without the app's entitlement file, so a sidecar that needs an entitlement (JIT, camera, microphone) does not get it under the hardened runtime. The packager has no per-sidecar entitlements, so keep such work in the app process or in a binary that needs none. Notarization covers them. On Windows, bundled `.exe` sidecars and addons are included in Authenticode signing; on Linux there is no signing step.

Without an identity, builds are ad-hoc signed: they run on your machine, but Gatekeeper blocks them once downloaded. To check a signed build:

```sh
codesign --verify --deep --strict .desktop/dist/<App>.app
xcrun stapler validate .desktop/dist/<Exe>-<version>-darwin-<arch>.dmg
```

The same options can live in the config:

```ts desktop.config.ts
sign: { identity: 'Developer ID Application: You (TEAMID)', notaryProfile: 'notary' },
```

<Steps>
  <Step title="Get a Developer ID certificate">
    A **Developer ID Application** certificate in your keychain. `bunx kitop doctor` lists the identities it finds.
  </Step>
  <Step title="Store notary credentials">
    Create a keychain profile with Apple's `xcrun notarytool store-credentials notary`, then pass its name as `NOTARY_PROFILE` (or `sign.notaryProfile`).
  </Step>
  <Step title="Build">
    Set `CODESIGN_IDENTITY` (or `sign.identity`) and build. `bunx kitop preflight .desktop/dist/<App>.app` runs the same pre-flight on any bundle.
  </Step>
</Steps>

**Universal builds.** `build: { universal: true }` builds both arm64 and x64 slices (Bun cross-compiles the other executable slice) and lipos the executable, `libshell`, the plugins and compiled addons into one app. Prebuilt addons must already contain the slices you need; sidecars are copied without merging architectures.

**Smaller builds.** `build.trim` drops the Bun APIs your app never calls (about 45 MB), and `build.aot` compiles to machine code at build time, which uses less memory. Both need a Bun that supports `--trim` and `--aot`: today that is canary, not stable, so default builds are larger. Point `build.bun` or `KITOP_BUN` at a canary binary; `bunx kitop doctor` reports whether yours qualifies. When available, `trim` is on by default (`trim: false` opts out, and the packager retries without it if the target runtime rejects it); `aot` is opt-in with `build: { aot: true }`, and is skipped for the other slice of a universal build and for Windows builds.

## Windows

```sh
KITOP_TARGET=windows bunx --bun vite build
```

| Output | |
| --- | --- |
| `<appName>-windows-<arch>/` | `<Exe>.exe` (icon and version resources), `shell.dll`, optional `app-native.dll`, language plugins under `plugins/`, addons, sidecars |
| `.zip` | The folder |
| NSIS installer | Per-user, with URL schemes and file associations |
| `release/` | Update archives, when `update` is set |

Cross-builds run the native toolchain (llvm-mingw, the WebView2 SDK, NSIS, osslsigncode) in Docker, so a running Docker is required; the first build creates the toolchain image, which takes a few minutes. Without Docker the build fails if `shell.dll` has to be built, and skips the installer, native plugins and addons with a warning. Authenticode signing is on when you give a signing tool or a certificate. Certificate authorities have only issued keys on hardware or in cloud services since 2023, so a new certificate usually needs your own tool. It runs once per file and signs it in place:

```ts desktop.config.ts
sign: { windows: { command: ['AzureSignTool', 'sign', '--azure-key-vault-url', vaultUrl, '{file}'] } },
```

The tool has to be on the machine that builds. The build signs before it makes the installer and the update archive, so what's published is what was signed. With an older exportable certificate, `osslsigncode` signs it for you:

```ts desktop.config.ts
sign: { windows: { certificateFile: 'cert.pfx', password: process.env.CERT_PASSWORD } }, // or $WINDOWS_CERT_PFX + $WINDOWS_CERT_PASSWORD
```

Rust and Go plugins are skipped when cross-building Windows from another OS; build on Windows if your app needs them. C/C++ plugins and source addons use the Docker toolchain.

`timestampUrl` defaults to `http://timestamp.digicert.com`. Data lives in `%APPDATA%\<identifier>`, caches and logs in `%LOCALAPPDATA%`. `build.targetArch` is `x64` (default) or `arm64`.

:::warning
CI runs the app and its notifications on a real Windows runner, which doesn't cover everything: validate the installer and app on a real Windows desktop. Unsigned Windows builds also trigger SmartScreen warnings. See [Limitations](/shipping/limitations).
:::

## Linux

```sh
KITOP_TARGET=linux bunx --bun vite build
```

| Output | |
| --- | --- |
| `<appName>/` | Relocatable app directory: the executable, `lib/` (`libshell.so`, plugin, addons), sidecars, `<identifier>.png`, `<identifier>.desktop`, `.kitop-app` |
| `<exe>-<version>-linux-<arch>.tar.gz` | The directory |
| `<exe>-<version>-linux-<arch>.AppImage` | When `appimagetool` is on the PATH |
| `release/` | Update archives and a manifest when [`update`](/shipping/self-update) is set: the directory under `linux-<arch>`, the AppImage under `appimage-<arch>`; unsigned without a private key |

GTK 3 and WebKitGTK 4.1 come from the system, like the system WebKit on macOS; libnotify, appindicator and libsecret are optional. `fileTypes` become the `.desktop` MimeType entry (plus a shared-mime-info package for custom types). C/C++ plugins and source addons need a Linux host of the target architecture; run the build there or in a matching Linux container. Prebuilt `addons` are copied. Rust and Go plugins need a host of the target OS. See [plugin platforms](/native/plugins/platforms).

Distribute the `.tar.gz`, the `.AppImage` or both: each updates itself as long as the user can write to where it's installed, so unpack the directory under the home directory rather than `/opt`. See [Self-update](/shipping/self-update#linux). The build doesn't make deb, rpm or Flatpak packages.
