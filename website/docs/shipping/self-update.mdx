---
title: Self-update
description: Signed updates from a static host, verified downloads, delta patches and a post-exit install helper.
---

The updater fetches a signed `update.json` from any static host (S3, R2, GitHub Releases, a CDN), downloads a SHA-256-pinned archive or a delta patch, swaps the app after it quits and relaunches it. Delta reconstruction also verifies each resulting file. See the platform and rollback limits below.

<Steps>
  <Step title="Create a key pair">
    ```sh
    bunx kitop keygen --out updater.key   # writes updater.key (0600) and updater.key.pub
    ```
    Keep the private key out of git, in your CI secret store.
  </Step>
  <Step title="Configure the feed">
    ```ts desktop.config.ts
    update: {
      manifestUrl: 'https://updates.example.com/notes/{channel}/update.json',
      publicKey: 'q1r…base64…=',           // contents of updater.key.pub
      channel: 'stable',
      privateKey: './updater.key',          // a file path (or $KITOP_UPDATE_KEY); used by vite build only
      baseUrl: 'https://updates.example.com/notes/stable/',
    },
    ```
  </Step>
  <Step title="Build and upload">
    `vite build` writes `release/<version>/` with the archive (and a delta patch from the previous release found in `release/`) and a signed `release/update.json`. Without a key file (unset, or the path doesn't exist) the build logs a `release` line and writes `release/update.unsigned.json` instead of `update.json`; sign it separately, for instance with `release merge` in [CI](/shipping/release). `notes` and `minimumVersion` are not written by `vite build`: they come from `release merge --notes` and `--minimum-version`. Upload the archives first and `update.json` last, so clients never see a manifest pointing at missing files. To build every platform and publish from CI, follow [Release with CI](/shipping/release).
  </Step>
  <Step title="Check from the app">
    ```svelte
    <button onclick={() => host.update.check().catch(() => {})} disabled={host.update.checking}>Check for updates</button>
    {#if host.update.checkError}
      <p>Couldn't check: {host.update.checkError.message}</p>
    {:else if host.update.available}
      {@const update = host.update.available}
      <p>Version {update.version} is available.</p>
      <button onclick={() => update.downloadAndInstall()}>Install and relaunch</button>
    {:else if host.update.upToDate}
      <p>Up to date.</p>
    {/if}
    ```
  </Step>
</Steps>

`check()` resolves the available update or `null`. An update has `version`, `currentVersion`, `notes`, `date`, `mandatory` (the installed version is older than the manifest's `minimumVersion`) and `downloadAndInstall()`. `check()` rejects when the feed can't be used (network error, invalid signature, wrong channel) and records the error in `host.update.checkError`. Checking is opt-in: nothing hits the network until you call it. When installation starts, the app quits and relaunches on its own; there is no progress callback.

## Platform support

| Platform | Current behavior |
| --- | --- |
| macOS | Full `.app` replacement and delta patches; the parent install directory must be writable |
| Windows | Full-archive file replacement through a PowerShell helper; no delta application. Confirmation and rollback work as on macOS. |
| Linux | The app folder from the `.tar.gz` is replaced whole, with delta patches; an AppImage is replaced as one file. Both roll back. See [Linux](#linux). |

## Linux

A Linux release has two artifacts per architecture, and a running copy takes the kind it is:

| Install | Manifest key | It knows because | The swap |
| --- | --- | --- | --- |
| The app folder from the `.tar.gz` | `linux-x64`, `linux-arm64` | `.kitop-app` is next to its executable | The whole folder moves to `<folder>.old` and the new one takes its name. Nothing of the old version stays. |
| AppImage | `appimage-x64`, `appimage-arm64` | `$APPIMAGE`, with its executable under `$APPDIR` | `<file>` is kept as `<file>.old`, and one rename replaces it. |

What can fail or take time comes first: the new copy goes next to the install, which is a real copy if the updater's data is on another filesystem, and the install isn't touched until that's done. Then an AppImage is one atomic rename, so the file is always there. A folder is two renames, so there's an instant between them with no folder. If the helper dies in that instant, the backup is still at `<folder>.old`, and that's the name to put back by hand.

- **Installed names stay.** A folder or AppImage the user renamed keeps its name, so `notes-1.4.0.AppImage` still has that name after updating to 1.5.0. Links and `.desktop` files keep working. The executable's name inside the folder has to stay the same from one release to the next, so changing `appName` means a manual install.
- **The folder belongs to the app.** Nothing kept inside it survives an update. App data is elsewhere already.
- **An executable copied out of the folder** doesn't update: it has no `.kitop-app`, so the feed's folder archive answers `layout_invalid` and nothing is touched.
- **A release built without `appimagetool`** has no `appimage-<arch>` key. AppImage installs then see no update for that release; they don't take the folder.

**Installs the user can't write to.** `/opt`, `/usr` and anything else this user doesn't own answer `not_writable` when installing, before anything is downloaded. Nothing changes and the app keeps running. For an app folder, both the folder and its parent have to be writable. `check()` still reports the update, so the app can say where to get it:

```ts
try {
  await update.downloadAndInstall();
} catch (error) {
  if (error.code === 'not_writable') showDownloadLink(); // the administrator or the package manager updates this one
  else throw error;
}
```

## Security

- **Signed manifest.** The client verifies the ed25519 signature before reading any field, then checks the app identifier (`identifier`, stored as the manifest's `name`), the channel, and that the version is strictly newer (an old signed manifest can't downgrade anyone).
- **Pinned artifacts.** Every archive's sha256 and size are in the signed manifest and checked while streaming. A compromised CDN can cause a failed update, not a malicious one.
- **Key rotation.** Ship a release embedding `[oldKey, newKey]`, then sign with the new key, then drop the old one.
- Code signing and notarization are separate and still needed for Gatekeeper and SmartScreen.

## Delta updates

With a previous release in `release/`, `vite build` also writes a `.sdpatch`: per-file operations (unchanged, rsync-style delta, new) with the size and sha256 of every resulting file. A macOS app or Linux app folder on that version downloads the patch, rebuilds the new app from its installed copy, verifies every file and applies it like a full update; any mismatch falls back to the full archive. AppImages and Windows always download the full archive.

## Install and rollback

The install is swapped by a helper after the app exits, and the previous copy is kept as `.old`. Each launch of a new version counts before anything else runs, and the version is confirmed once its first page has stayed up for 5 seconds, or at a clean quit after that page. If it doesn't get there twice, the shell restores the previous copy, starts it, and skips that version in future checks. So a version that crashes in its native layer or never shows a page is replaced, and so is one whose server dies before it's confirmed, since the app [restarting after a crash](/concepts/architecture#when-something-crashes) is a launch too. A crash after that doesn't undo the confirmation. A page that loads but misbehaves counts as healthy: the shell can't tell, so test your releases. If the executable can't be launched by the OS at all, nothing of it runs, so nothing is restored.

CI runs this on macOS, Windows and Linux with real builds: an update that applies, a version that crashes at once, and one whose server dies while it loads. Those builds aren't signed and the feed is a local folder, so signed updates and real hosting are still yours to try before you rely on them.

Applications that call `createUpdater()` directly own the timing of `rollbackIfNeeded()`, `confirm()` and the restart: see `src/updater/README.md`.

The install directory must be writable by the user: `/Applications` for an admin on macOS, a per-user location on Windows (the NSIS installer is per-user), a directory the user owns on [Linux](#linux). A translocated (quarantined) macOS app is refused.

For manual control (custom download UI, publishing from CI), the lower-level `createUpdater()` from `@kitop/shell/updater` and the `updater-cli.ts` script in the shell package (`keygen`, `sign`, `verify`, `pack`, `make-manifest`) are documented in the package's `src/updater/README.md`.
:::
