title: Limitations

Desktop only: macOS, Windows, Linux. iOS can't run Bun, so mobile isn't a target; for mobile, deploy the SvelteKit app and ship it as a PWA or wrap it (e.g. Capacitor).

## Everywhere

- **Smaller builds need a canary Bun.** `build.trim` and `build.aot` are unavailable on stable Bun. See [Distribution](/shipping/distribution#macos).
- **Ops vary by platform.** Many window and app ops are macOS-only, or macOS and Linux, and answer `unsupported` elsewhere. `host.capabilities.describe()` lists the operations registered in the running build; a registered operation can still reject because the OS, permission or runtime is unavailable.
- **No screen reader has been run.** axe-core and real key presses check what the framework draws, on Linux only. See [Accessibility](/ui/accessibility).
- **Self-update has platform and recovery gaps**: no delta patches on Windows or for AppImages, no recovery from an executable the OS can't launch at all. See [Self-update](/shipping/self-update#platform-support).

## macOS

- **Notarization needs credentials.** The pipeline implements pre-flight, `notarytool` submission and stapling; it runs only with a signing identity and a notary profile.
- **Permission names exceed runtime support.** Usage strings can be declared for every documented name, but `host.permissions.status()` checks only `camera`, `microphone`, `notifications`, `screenRecording`, `accessibility`, `inputMonitoring` and `fullDiskAccess`. Other declared names reject with `invalid_args`; WebKit page consent is separate. Full Disk Access reports `unknown` when its probe cannot establish a grant. See [Permissions](/features/permissions).
- **Screen capture** needs macOS 12.3 for source discovery, Screen Recording permission and macOS 14 for stills.
- **Notifications need a bundled app.** Under `vite dev`, notification calls return `unavailable`; location and speech consent also need testing in a built bundle.
- **Some WebKit delegates use private SPI.** Location, speech and display-capture consent can vary with the installed macOS/WebKit version.
- **The macOS 26 icon** (`Assets.car`) needs Xcode 26. See [App icon](/shipping/app-icon).

## Windows

- **Tested on a Windows runner, not on a PC:** CI runs end-to-end tests on a Windows runner for notifications, windows, title-bar dragging, menus, tray, dialogs, clipboard, views, background jobs, MCP, relaunch, permissions, downloads, printing, navigation policy, cookies, authentication, certificates, find, JavaScript dialogs, media, crash recovery, file drop, `clearData`, sessions, proxies, custom protocols, content rules, registered scripts, the input policy, the cancellable quit, process metrics, the app's icon and activation policy, the rich clipboard, route dialogs, the jump list, bookmarks and dragging files out. High-DPI and multi-monitor setups aren't covered, since the runner has one display at 100%, and only x64 runs: arm64 is compiled. Test your app on a real PC.
- **Windows differs where WebView2 does:** a paused download resumes only in the run that started it, `host.webview.download` needs an attachment from another origin, a navigation policy holds the navigation with a bounded wait, `fileDragEnter` has no paths, `clearData` reaches the sites views loaded, a custom protocol's response reaches the page whole when it ends and a request going away isn't noticed before its document does, a proxy can't change while a view is open in its session and the default session can't have one, content rules have no `block-cookies` and don't reach WebSockets, and the input policy only has keys held with Control or Alt and keys that make no character. See [downloads](/host/web/downloads#platform-support), [navigation policy](/host/web/web-content#platform-support), [web view](/host/web/webview#platform-support), [web policy](/host/web/web-policy#platform-support), [protocols](/host/web/protocol#platform-support), [sessions](/host/web/sessions#windows), [content rules](/host/web/web-content#rules-on-windows) and [input policy](/host/input/input-policy#platform-support).
- **What the runner couldn't show:**
  - A real logoff or shutdown, which would end the machine running the tests. The messages a session sends were sent by another process, and the Restart Manager really closed the app and was really refused. See [Windows sessions](/host/app/app#windows-sessions).
  - A share target. The sheet opens, and on the runner says it can't list where to share, so no app has received anything. Its data was accepted, and closing it answers `null`. See [shell](/host/os/shell#shareitems-windowid).
  - Windows Hello's prompt. The runner has no Hello: only its `available: false` path has run. See [secure storage](/host/os/secure-storage#authenticatereason-options).
  - A jump list task starting a closed app, whose `menuAction` waits for its first page. A running app gets it, from the real list and from what the list stores.
- **Windows differs where Windows does:** `dialog.sheet` doesn't dim or slide. A jump list is flat: submenus are refused, disabled items are left out, `checked` isn't shown, and a task has the executable's icon. A bookmark can't follow a file to another volume. `biometricsOnly` is refused, as Windows Hello's PIN is always a way in, and `biometrics` says `windowsHello` for a PIN too. `accessory` windows have a small title bar. A real session end gives quit phases about 4 seconds, and server cleanup after them isn't sure to finish.
- `host.system.getAccessibility` reports `differentiateWithoutColor` as `false`: Windows has no such setting. Its color filters change the screen, and say nothing of what an app should draw.
- Not available:
  - `app.hideOthers`: Windows has no such idea of hiding another app. It rejects with `unsupported`.
  - `shell.previewFile`: Windows has no system previewer. Opening the default app under this name would be something else, and `shell.openPath` does that. It rejects with `unsupported`.
  - `power.getThermalState`: no public Windows call says this. It rejects with `unavailable`, and `thermalStateChanged` never fires.
  - `permissions.guide`, `guideState`, `cancelGuide`: no system panel to float a guide over, nor anything to drag into it. They reject with `unknown`, and `host.permissions.guide()` opens the settings page and reads the status.
  - `notifications.simulateResponse`, `window.testScroll`: test-only hooks of the macOS build. They reject with `unsupported`.
  - These `window` calls reject with `unsupported`: a parent after creation (`setParent`, `getParent`, `getChildren`), `getLevel`, `setAspectRatio`, `setFocusable`, `setMovable`, `setHasShadow`, `setSimpleFullscreen`, `setVisibleOnAllWorkspaces`, `setRepresentedFilename`, `showCharacterPalette` and `controlsArea`, with their getters, and macOS's own materials and traffic lights. They haven't been looked at for Windows.
- The WebView2 runtime must be installed. The shell offers an Evergreen download link when it is missing; it does not bundle the runtime.
- Rust and Go plugins need a Windows host. See [Distribution](/shipping/distribution#windows).
- Windows repeating notifications queue at most 128 occurrences over the next 30 days, topped up while the app runs. They do not repeat indefinitely while closed.

## Linux

- Tray hosts don't report icon positions, so tray-anchored popovers open at the pointer.
- On Wayland, global shortcuts and screen capture go through the desktop portal (`GlobalShortcuts`, `Screenshot`). They've run in a real Wayland session on a headless compositor, against a stand-in that follows the portal's request and response protocol. **No real portal has been exercised.** See [shortcuts](/host/input/shortcuts#wayland) and [capture](/host/os/capture).
- `shell.previewFile` needs GNOME's previewer (`org.gnome.NautilusPreviewer`), and has only run against a stand-in. `shell.startDrag` and the sheet's placement have only run on X11, under openbox. See [shell](/host/os/shell).
- The quit reasons `logout`, `shutdown` and `system` don't occur: a session ending arrives as a signal, or not at all. A dock's badge is a number, its progress has no colors, and the icon set by `setDockIcon` is the windows', not the dock's own. The launcher's signal has been read on the bus; no real dock has shown it. See [host.app](/host/app/app).
- A bookmark follows a rename within its folder, not a move to another one. See [files](/host/os/files#linux).
- `app.metrics` can't say which window a web process draws: WebKitGTK doesn't expose it, so there's no `windowId`.
- `power.getThermalState` rejects with `unavailable` on machines without thermal trip points, and it has run on files laid out like sysfs, in a container. `power.getSystemIdleTime` needs X11 and `libXss.so.1`. See [power](/host/app/power).
- `host.system.getAccessibility` reports `differentiateWithoutColor` and `reduceTransparency` as `false`: Linux has no such settings.
- Not available, each rejecting with `unsupported`:
  - `app.hideOthers`: other applications' windows belong to the window manager, on X11 and Wayland.
  - `menu.setDockMenu`, `getDockMenu`: docks build their menus from the `.desktop` file. The launcher signal's `quicklist` could carry one from a DBusMenu server, which isn't done.
  - `shell.share`: Linux desktops have no system share menu.
  - `secureStorage.authenticate`, `system.biometrics`: there's no desktop-wide way for an app to ask who the user is. polkit needs an action installed as root, and `fprintd` only knows fingerprints.
  - `permissions.guide`, `guideState`, `cancelGuide`: there's no privacy panel to walk the user through. `host.permissions.guide()` falls back as on Windows.
  - `notifications.simulateResponse`, `window.testScroll`: test-only hooks of the macOS build.
- C/C++ plugins, source addons, Rust and Go plugins need a Linux host. See [Distribution](/shipping/distribution#linux).
- Native inline notification replies are unavailable; reply buttons become plain actions. Scheduling catches up when the app restarts rather than delivering while it is closed.
- The build makes an app folder and an AppImage, not deb, rpm or Flatpak packages. Self-update covers those two; an install this user can't write to, in `/opt` for instance, answers `not_writable`. See [Self-update](/shipping/self-update#linux).
- A navigation policy can't tell frames from the main frame: `isMainFrame` is `null`. See [web content](/host/web/web-content#platform-support).
- Permission requests name neither origin nor frame, certificate exceptions take effect on top-level loads, and there are no client identities. See [web policy](/host/web/web-policy#platform-support).
- `pauseMedia` and `getMediaState` reach what the page's document and same-origin frames hold, and `new Audio()`. `onLifecycle` only reports `terminated`. A page's DOM `drop` has no `files`; `onFileDrop` has the paths. See [web view](/host/web/webview).
- Camera, microphone and screen requests have been run on WebKit's mock devices, under Xvfb. Real devices, the desktop's screen-share portal and location through GeoClue haven't been covered.
- A paused download keeps nothing: `resume` downloads the whole file again, which only a GET over http(s) can do. WebKitGTK can't pause and can't ask a server for a range. See [downloads](/host/web/downloads#platform-support).
- Printing has been run against GTK's real print dialog and its CUPS backend talking to a small IPP server in the test, under Xvfb. A real printer and `cupsd` haven't been covered. `copies` are in the document WebKit sends, not an option of the job. See [web view](/host/web/webview#printoptions).
- A custom protocol's handler isn't told when a request goes away before it answers, only once its response has started. See [protocols](/host/web/protocol#platform-support).
- An input policy's `meta` is the Super key and `keyCode` a hardware key code. It has been run with real X11 key events under Xvfb, not on Wayland. See [input policy](/host/input/input-policy#platform-support).
- A plain HTTP proxy receives `http://` requests directly rather than through CONNECT. See [sessions](/host/web/sessions#platform-support).
- Self-update has been run through real updates and rollbacks on Ubuntu 24.04 only, under Xvfb. Other distributions and real desktop sessions haven't been covered.

## Tooling

- `kitop doctor` checks each OS's tools, and signing on macOS only. It is not a complete cross-platform readiness check.
- SVG icon sources require macOS (`sips`); use a PNG source when building the same app in Linux or Windows CI.
- Swift and Objective-C plugins are macOS-only. Only one Go plugin runtime is allowed per app process; consolidate Go code into one module. See [Native code](/native).
