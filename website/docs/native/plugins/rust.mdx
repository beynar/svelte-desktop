A Rust plugin runs inside the shell process, with a new native thread for each command call. Pick it for Rust crates and CPU or I/O work callable from both pages and SvelteKit server code. Use a [sidecar](/native/sidecars) for process isolation. Shared rules (names, errors, events, `bridge.allow`, dev restarts) are on [Plugins](/native/plugins); toolchains and builds per OS are on [Platforms](/native/plugins/platforms).

## Quick start

```sh
bunx kitop add rust
```

This creates `native/rust/Cargo.toml`, `native/rust/src/lib.rs` and a `.gitignore` for `target/`, with a starter command `hello.rust`. It refuses to overwrite an existing `native/rust`. Install Cargo and a Rust that supports edition `2024`.

For dependencies, keep the crate (`crate-type = ["cdylib"]`); a folder with its own `Cargo.toml` is one plugin, and several are allowed. A single loose `.rs` file under `native/` also works and becomes its own crate. The example below hashes a document and reports progress. Replace the manifest and library:

```toml native/rust/Cargo.toml
[package]
name = "document-checksum"
version = "0.1.0"
edition = "2024"

[lib]
crate-type = ["cdylib"]

[dependencies]
kitop = { path = "../../node_modules/@kitop/shell/native/sdk/rust" }
serde = { version = "1", features = ["derive"] }
ts-rs = "12"
sha2 = "0.10"
```

Keep the SDK path the CLI wrote if your installation differs.

```rust native/rust/src/lib.rs
use serde::{Deserialize, Serialize};
use sha2::{Digest, Sha256};
use kitop::{emit, log, plugin, Error, Plugin, TS};

#[derive(Deserialize, TS)]
struct HashArgs {
    #[serde(rename = "requestId")]
    request_id: String,
    text: String,
}

#[derive(Serialize, TS)]
struct Checksum {
    hex: String,
    bytes: u64,
}

#[derive(Serialize)]
struct Progress<'a> {
    #[serde(rename = "requestId")]
    request_id: &'a str,
    bytes: u64,
}

fn setup(p: &mut Plugin) {
    p.command("checksum.rust", |a: HashArgs| -> Result<Checksum, Error> {
        if a.request_id.is_empty() {
            return Err(Error::invalid_args("requestId is empty"));
        }
        let mut hasher = Sha256::new();
        let mut bytes = 0_u64;
        for chunk in a.text.as_bytes().chunks(64 * 1024) {
            hasher.update(chunk);
            bytes += chunk.len() as u64;
            emit("checksum.progress", &Progress {
                request_id: &a.request_id,
                bytes,
            });
        }
        log("Rust checksum complete");
        Ok(Checksum { hex: format!("{:x}", hasher.finalize()), bytes })
    });
    p.command("checksum.ready", |(): ()| -> Result<bool, Error> { Ok(true) });
}

plugin!(setup);
```

After `vite dev` writes `native.checksum.rust` to `src/native.d.ts`, call it from a page or server code. A call with bad arguments rejects with `invalid_args`.

```ts
import { native } from '@kitop/shell/native';
import { onPlatform } from '@kitop/shell/platform';

const requestId = crypto.randomUUID();
const off = onPlatform<{ requestId: string; bytes: number }>(
  'checksum.progress',
  (progress) => {
    if (progress.requestId === requestId) console.log(progress.bytes);
  }
);
try {
  const ready: boolean = await native.checksum.ready();
  const result = await native.checksum.rust({ requestId, text: 'A saved document' });
  console.log(ready, result.hex, result.bytes);
} finally {
  off();
}
```

`host.native` and `host.on` are the same without imports. For large files, pass a validated path and read incrementally in Rust instead of sending the contents through JSON.

## Type mapping

Rust uses Serde: derive `Deserialize` for arguments, `Serialize` for results, and `TS` (from `ts-rs`) for both. Arguments arrive as a JSON object; use a struct, or `()` for none. Results can be any serializable value with a `TS` representation. `ts-rs` writes inline types, and large integers (`u64`, `i64`) become TypeScript `number`: keep values within JavaScript's exact integer range, or use strings. Custom Serde serialization may not match the generated type, so check `src/native.d.ts`.

## SDK API

The crate is `kitop`, imported as `kitop`.

| Public item | Contract |
| --- | --- |
| `plugin!(setup)` | Exports the plugin entry points for `fn setup(p: &mut Plugin)`. |
| `Plugin::command(name, f)` | Registers `service.op` and returns `&mut Self`. `f: Fn(A) -> Result<R, Error> + Send + Sync + 'static`, with `A: DeserializeOwned + TS` and `R: Serialize + TS`. |
| `TS`, `Value` | Re-exports of the `ts-rs` trait and derive, and `serde_json::Value`. `Value` still needs the `TS` bounds. |
| `Error { code, message }` | The rejection. `Error::new(code, message)`, plus `invalid_args`, `unsupported`, `unavailable`, `denied` and `internal` constructors. Any `std::error::Error` converts to `internal`, so `?` works. |
| `emit(event, &data)` | Serializes and broadcasts the payload from any thread. Sends nothing before host initialization or on a serialization failure. |
| `log(message)` | Writes a line through the shell. |

Register commands in `setup`; a name without a dot panics. Setup also runs when the build reads the commands, so keep it to registration.

## Errors and panics

Bad JSON or a failed argument decode rejects with `invalid_args`; a returned `Err` keeps its code and message; a serialization failure is `internal`. A panic in decoding, the handler or serialization is caught and rejects with `internal` (`service.op panicked`). Not caught: `panic = "abort"`, process exit, memory faults, setup panics and panics in threads you spawn. Use a sidecar if a crash mustn't end the app.

## Threads and events

Each call runs on its own `std::thread::spawn` thread, not on a pool or the Bun Worker. Calls, even to the same command, can run at once, so shared state needs synchronization and handler state must be `Send + Sync`.

There is no async command, cancellation or timeout: a handler returns a `Result`. Block on its thread, and send progress with `emit`. With an async library, own its runtime and wait for the result inside the handler. The SDK can't run code on the UI thread or touch windows: emit an event, and let the page or server act on it.

## Dev and build

`vite dev` builds the host architecture in the debug profile into `.desktop/dev/native/`; `vite build` uses `--release`. Cargo output stays in `.desktop/cargo/`. Other crates and loose files are named from their path: `native/stats.rs` becomes `libapp-rust-stats.dylib` on macOS. Rust plugins build only on a host of the target OS; see [Platforms](/native/plugins/platforms) for paths, targets and signing.
