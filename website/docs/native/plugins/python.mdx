Python commands run in one Python process that the app starts and owns. Pick Python for its libraries: data work (numpy, pandas, polars), local models (torch, transformers, onnxruntime, mlx), or Python code you already have. Pages and server code call them through `host.native` like any other plugin command, with types generated from the annotations. The app ships its own CPython and dependencies, so users install nothing.

Use [Rust](/native/plugins/rust) or [Go](/native/plugins/go) for native computation inside the app process, or a [sidecar](/native/sidecars) for an existing executable with its own protocol.

## Setup

```sh
bunx svelte-desktop add python
```

This creates `native/python/` with a `pyproject.toml` and `hello.py`, which defines a `hello.python` command. Put your modules in that folder, and list their dependencies in `pyproject.toml`, or add them with `uv add <package>` from the folder:

```toml native/python/pyproject.toml
[project]
name = "my-app-python"
version = "0.0.0"
requires-python = ">=3.10"
dependencies = ["numpy>=2"]
```

The build uses [uv](https://docs.astral.sh/uv/) to create the environment and install the dependencies; install it once on the build machine. Commit `uv.lock`: uv writes it next to `pyproject.toml`, and builds install exactly those versions. Without `pyproject.toml`, the commands run on the standard library alone, with Python 3.12 or the version in `native/python/.python-version`.

The SDK requires Python 3.10 or later.

## Example: statistics on a page

```python native/python/stats.py
from dataclasses import dataclass

import numpy as np
from svelte_desktop import InvalidArgs, command, emit


@dataclass
class Summary:
    mean: float
    std: float
    count: int


@command("stats.summary")
def summary(values: list[float], trim: float = 0) -> Summary:
    if not values:
        raise InvalidArgs("values is empty")
    a = np.sort(np.array(values))
    cut = int(len(a) * trim)
    if cut:
        a = a[cut:-cut]
    return Summary(mean=a.mean(), std=a.std(), count=len(a))


@command("stats.progress")
async def progress(steps: int) -> int:
    for n in range(1, steps + 1):
        emit("stats.step", {"n": n, "of": steps})
    return steps
```

After `vite dev` starts, `src/native.d.ts` declares both commands:

```ts
const off = host.on<{ n: number; of: number }>('stats.step', (s) => console.log(s.n, '/', s.of));
const { mean, std, count } = await host.native.stats.summary({ values: [3, 1, 4, 1, 5], trim: 0.2 });
await host.native.stats.progress({ steps: 3 });
off();
```

`native` from `@svelte-desktop/shell/native` is the same object. Command names share one namespace with the other plugins: two languages can't register the same `service.op`.

## SDK API

Import `svelte_desktop`. In `vite dev`, the uv environment in `.desktop/python/venv` has the SDK on its path, so point your editor at that interpreter to resolve the import.

| Public item | Contract |
| --- | --- |
| `@command("service.op")` | Registers the function. Names are letters, digits, `_` and `-`, with one dot. A name defined twice raises at import. |
| `emit(event, data=None)` | Broadcasts `data` (JSON) to every page and to server code. Any thread. Event names: letters, digits and `_ . : / -`. |
| `log(message)` | Writes a line in the app's log. |
| `Error(message, code=None)` | Rejects the call with its code (`internal` by default). |
| `InvalidArgs`, `Unsupported`, `Unavailable`, `Denied` | `Error` subclasses with the matching code. |
| `commands` | The registered commands, by name. |

The app imports every top-level `.py` file of `native/python/` at startup. Packages are imported by those modules. Files named `test_*.py`, `*_test.py`, `conftest.py` and `setup.py`, and names starting with `_`, are not imported. Keep module-level code to imports and setup: it also runs when the build reads the commands.

### Arguments, results and errors

The call's argument object becomes the function's keyword arguments: `host.native.stats.summary({ values, trim })` calls `summary(values=..., trim=...)`. A parameter with a default is optional. A missing required argument or an unknown one rejects with `invalid_args`. A `**kwargs` parameter accepts any other keys. A dict passed for a parameter annotated with a dataclass or a pydantic model is built into that class; a field it refuses rejects with `invalid_args`. Other values arrive as JSON gives them: the SDK does not convert or check them against their annotations.

Results are encoded to JSON:

| Python value | JSON |
| --- | --- |
| `dict`, `list`, `tuple`, `str`, `int`, `float`, `bool`, `None` | As is. `NaN` and infinities become `null`. |
| Dataclasses, pydantic models (`model_dump(mode="json")`) | Objects |
| `Enum` | Its value |
| `set`, `frozenset`, generators and other iterables | Arrays |
| `datetime`, `date`, `time` | ISO 8601 strings |
| `Path`, `UUID` | Strings |
| `Decimal` | Numbers |
| `bytes` | Base64 strings |
| numpy arrays and scalars, torch tensors (`tolist()`, `item()`) | Arrays and numbers |

An `Error` rejects with its code and message, on one line. Any other exception rejects with `internal` and `ExceptionType: message`, and its traceback goes to the log. JavaScript receives a `NativeApiError`; see [errors](/host#errors). Page calls also pass `bridge.allow`.

## The Python process

The shell side of Python commands is a plugin like the others, `libapp-python`. It registers each command as a platform op when the app starts, and starts the Python process right away, so Python boots while the page loads. Calls are written to the process's stdin as JSON lines, and replies come back on its stdout. The process runs separately from the shell process: a crash in Python or in an extension module doesn't take the app down, and the GIL never blocks the window.

**Concurrency.** `def` handlers run on a pool of 8 threads (`SVELTE_DESKTOP_PYTHON_WORKERS` in the app's environment changes it). `async def` handlers run on one asyncio loop in its own thread. Concurrent calls overlap: protect shared state. Pure-Python CPU work holds the GIL, so it doesn't run in parallel with other handlers. numpy, torch and most native libraries release the GIL during their computations.

**Output.** `print()` and anything written to stdout or stderr, including by C libraries, goes to the app's stderr: the `vite dev` terminal, or the log file of a packaged app. The protocol uses a private copy of stdout, so output never corrupts it.

**Crashes.** When the process exits, its pending calls reject with `internal`, and the next call starts a new process. If it fails before it is ready, typically on an `ImportError`, the rejection includes the last lines of its stderr. State in the process (loaded models, caches) starts fresh.

**Quitting.** When the app quits or dies, the process's stdin closes and it exits immediately; running handlers don't finish. On Windows, the process is also in a job that ends with the app.

**Events.** `emit` works from any thread, including asyncio tasks and threads you start. Object payloads arrive as they are; others arrive as `{ value: payload }`. See [events](/host/data/events).

The process has no access to windows or the `host` API. Emit an event, or return a result, and let the page or server act on it. See [Threads and processes](/native/threads).

**Startup time.** The process is ready in about 60 ms with the standard library. Heavy imports add their own time (torch takes seconds), and calls wait for them. To keep the first calls fast, import heavy libraries inside the commands that need them.

## Generated TypeScript

The build imports the modules with the app's interpreter and reads each command's signature (`python -m svelte_desktop describe`). Parameters become the argument object; a function without parameters takes no arguments.

| Annotation | TypeScript |
| --- | --- |
| `str`, `bytes`, `datetime`, `date`, `time`, `UUID`, `Path` | `string` |
| `int`, `float`, `Decimal` | `number` |
| `bool` | `boolean` |
| `None` | `null` |
| `list[T]`, `set[T]`, `Sequence[T]`, `tuple[T, ...]` | `T[]` |
| `tuple[A, B]`, `NamedTuple` | `[A, B]` |
| `dict[str, T]`, `Mapping[str, T]` | `Record<string, T>` |
| `X \| Y`, `Optional[X]` | `X \| Y`, `X \| null` |
| `Literal["a", "b"]`, `Enum` | Unions of literals |
| `TypedDict` (`Required`, `NotRequired`, `total`) | Objects with optional fields |
| Dataclasses, pydantic models | Objects; in arguments, fields with defaults are optional |
| `Annotated[T, ...]` | `T` |
| `Any`, no annotation, recursive types, other classes | `unknown` |

`from __future__ import annotations` and string annotations are supported. Annotations that can't be resolved make that command's types `unknown`.

## Dev and build

`vite dev` runs `uv sync` into `.desktop/python/venv`, writes the bridge and its manifest to `.desktop/dev/native/`, and generates `src/native.d.ts`. The modules run from `native/python/` in place.

Saving a `.py` file, `pyproject.toml` or `.python-version` reads the commands again and syncs the dependencies:
- **Same commands:** only the Python process restarts, and the page keeps its state.
- **Commands added, removed or renamed:** the window restarts.

Calls pending at the restart reject. `uv.lock`, `__pycache__` and the environment are ignored.

`vite build` on macOS:

1. syncs an environment without dev dependencies (`uv sync --no-dev`) from a uv-managed CPython;
2. copies that CPython to `Contents/Resources/python/runtime`, without its headers, Tcl/Tk, test suite, pip and `libpython`;
3. copies the dependencies to `site-packages/`, the SDK to `sdk/`, and your modules to `app/` (tests, `pyproject.toml` and `uv.lock` excluded);
4. compiles every module to bytecode, then signs each executable and library with the app.

The bridge goes in `Contents/Frameworks/plugins/libapp-python.dylib`. The standard library adds about 38 MB; dependencies add their own size (numpy about 35 MB, torch several hundred).

The packaged interpreter runs with `-I`: the user's `PYTHONPATH`, `PYTHONHOME` and user site-packages are ignored. It runs with `-B` too, so it writes no bytecode into the signed bundle.

| Platform | Dev | Packaged |
| --- | --- | --- |
| macOS | ✓ | ✓, one architecture: the build machine's |
| Linux | ✓ (needs a C++ compiler) | Not yet: the commands are missing from the package |
| Windows | Not yet | Not yet |

A universal macOS build (`build.universal`) fails with Python commands: build arm64 and x64 separately, each on a machine of that architecture. GPU support is the libraries' own: torch uses Metal (MPS) on Apple silicon without extra setup.
