title: Platforms and configuration
description: Which plugin languages build on which OS, cross-compiling, and where plugins land in the package.

Use `macos/`, `linux/` and `windows/` folders under `native/` when a plugin needs a different implementation per OS, and keep the same `service.op` contract. A target builds the shared sources plus its own folder. For how plugins work in general, see [Plugins](/native/plugins).

## Languages by OS

| Language | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Swift | Yes | No | No |
| Objective-C / Objective-C++ | Yes | No | No |
| C / C++ | Yes, through Objective-C or Swift setup | Yes | Yes (production only) |
| Rust | Yes | Yes | Yes |
| Go | Yes | Yes | Yes |
| Python | Yes | Dev only | No |

- Keep Swift, `.m` and `.mm` files under `macos/`. On Linux they are skipped. On Windows they cause the whole C-family library to be skipped.
- On macOS the build supplies its own `sd_plugin_init`, so a raw C entry point works only on Linux and Windows. See the [C ABI](/native/plugins/objective-c-and-c#the-c-abi).
- Native-window dev builds C-family plugins on macOS and Linux only, for the host architecture. Windows C/C++ plugins build for production but not in dev.
- Rust needs Cargo, a target and its linker; Go needs Go 1.22 or later and a C toolchain for cgo. The build doesn't install toolchains. A missing Rust target prints a `rustup target add <triple>` hint.
- Python needs [uv](https://docs.astral.sh/uv/) and a C++ compiler. Packaged apps with Python commands are macOS only.

## Cross-compiling

| Library | Limit |
| --- | --- |
| macOS Swift / C-family | Needs macOS and the Apple SDK. |
| Linux C/C++ | Builds on a Linux host of the same architecture; otherwise skipped with a warning. Use a matching Linux machine or container. |
| Windows C/C++ | Builds in Docker with an llvm-mingw image, also from macOS or Linux. Without Docker it is skipped with a warning. |
| Rust and Go | Built only when the target OS is the host OS; other targets are skipped with a warning. Changing architecture on the same OS needs that target's toolchain. |
| Python | One architecture per macOS build: the build machine's. `build.universal` fails with Python commands. |

Cross-compiling the Bun executable doesn't build the plugins. Check the build output and the package before shipping.

## Architectures

`build.universal: true` on macOS builds `arm64` and `x64` and joins them with `lipo`; Rust also needs `aarch64-apple-darwin` and `x86_64-apple-darwin` installed, and Go needs cgo working for each. Linux and Windows build one architecture per run (`build.targetArch`).

`build.minimumSystemVersion` (default `12.0`) sets the macOS deployment target of every plugin. It doesn't lower the app's own requirement, and a dependency may need a newer macOS. Linux needs GTK 3 and WebKitGTK 4.1; Windows needs the WebView2 runtime.

Other build options (`build.target`, `outDir`, `sign`, `permissions`, `addons`, `sidecars`) are in the [config reference](/reference/config). There are no plugin-specific compiler or linker options.

## Bundle paths

Relative to the app bundle or directory:

| Artifact | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Shell | `Contents/Frameworks/libshell.dylib` | `lib/libshell.so` | `shell.dll` |
| C-family plugin | `Contents/Frameworks/libapp-native.dylib` | `lib/libapp-native.so` | `app-native.dll` |
| Rust and Go plugins | `Contents/Frameworks/plugins/libapp-<name>.dylib` | `lib/plugins/libapp-<name>.so` | `plugins/app-<name>.dll` |
| Python bridge | `Contents/Frameworks/plugins/libapp-python.dylib`, runtime in `Contents/Resources/python` | Not packaged | Not packaged |

`<name>` comes from the project's path under `native/`: `native/rust/` gives `rust`, `native/stats.rs` gives `rust-stats`.

## Signing

- **macOS:** nested libraries, including every `plugins/` entry, are signed before the app bundle. The identity is `sign.identity`, then `CODESIGN_IDENTITY`, otherwise ad-hoc. Notarization is configured under `sign`.
- **Linux:** plugin libraries aren't signed.
- **Windows:** Authenticode signing (optional, `sign.windows`) covers the executable, shell, C-family plugin, addons and sidecars, but not the Rust and Go DLLs under `plugins/`.
