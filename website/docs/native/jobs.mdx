title: Background jobs

A job runs finite work in a separate Bun process and reports progress and one result. Pick it for CPU-heavy calculations or long tasks that should not block the SvelteKit server. Use a [service](/native/services) when a child must keep state and accept commands, or a [sidecar](/native/sidecars) for an existing executable.

API references: [`host.jobs`](/host/data/jobs) and [server code](/host/data/server).

## Define and start a job

Put one entry file per job directly in `src/jobs/`. This example hashes a list of texts and returns their digests:

```ts src/jobs/hash-texts.ts
// No import: HostJob is a global type.
const hashTexts: HostJob<{ texts: string[] }, { digests: string[] }> = async ({ texts }, ctx) => {
  const digests: string[] = [];
  for (const [i, text] of texts.entries()) {
    ctx.signal.throwIfAborted();
    digests.push(new Bun.CryptoHasher('sha256').update(text).digest('hex'));
    ctx.progress((i + 1) / texts.length, `Hashed ${i + 1} of ${texts.length}`);
    // Let the child receive cancellation messages between CPU-bound items.
    await Bun.sleep(0);
  }
  ctx.log('Hashed', digests.length, 'texts');
  ctx.emit({ count: digests.length });
  return { digests };
};
export default hashTexts;
```

Start it from server code (a remote function, an endpoint, a hook):

```ts src/routes/api/hash-texts/+server.ts
import { json } from '@sveltejs/kit';

export function POST() {
  const job = host.jobs.start('hash-texts', { texts: ['hello', 'world'] }, { concurrency: 2 });
  return json({ id: job.id, state: job.state });
}
```

`start` returns a record immediately. It can already be `running` or `failed`, rather than `queued`. Server code can use `await host.jobs.wait(job.id)` to get the terminal record. It resolves for `done`, `failed` and `canceled`; inspect `state` before using `result`.

Start and watch it from a page:

```svelte
<script lang="ts">
  import { onMount } from 'svelte';

  let status = $state('');
  onMount(() => host.jobs.on('done', (job) => { status = `${job.name} finished`; }));

  async function start() {
    try {
      const response = await fetch('/api/hash-texts', { method: 'POST' });
      if (!response.ok) throw new Error(`Start failed: ${response.status}`);
    } catch (error) {
      status = error instanceof Error ? error.message : String(error);
    }
  }
</script>

<button onclick={start}>Hash texts</button>
<p>{status}</p>
{#each host.jobs.active() as job (job.id)}
  <progress max="1" value={job.progress}></progress> {job.message}
  <button onclick={() => host.jobs.cancel(job.id)}>Cancel</button>
{/each}
```

## API

Pages expose a reactive mirror of job records and events. Server code owns the job registry and also has `start` and `wait`. The methods have some different return types; see [`host.jobs`](/host/data/jobs).

| | |
| --- | --- |
| `start(name, args, { concurrency, env })` | Server only. Queue `src/jobs/<name>.ts` or `.js`. Use JSON-serializable arguments and results. `concurrency` defaults to unlimited. |
| `wait(id)` | Server only. Resolves when the job ends; rejects for an unknown id. |
| `list()`, `active()`, `running()`, `get(id)` | Snapshots in server code; reactive in pages. A missing `get` is `null` on the server and `undefined` in a page. |
| `cancel(id)` | Server returns a boolean; a page sends a cancellation request and returns `Promise<null>`. Queued jobs end immediately. Running jobs receive cancellation, then a kill attempt after 2 s if still tracked. |
| `on(state, fn)` | State transitions: `queued`, `running`, `done`, `failed`, `canceled`, or `'*'` |
| `onEvent(fn)` | Custom events from `ctx.emit(data)` |

A server job record contains `id`, `name`, `state`, `progress` (0 to 1), `message`, `args`, optional `result`, `error` and `pid`, `log`, `createdAt`, optional `startedAt` and `endedAt`, and `restored: true` for restored history. Timestamps are Unix milliseconds. Page records expose the shared job fields; the page type does not declare `pid` or `restored`. Events are not replayed to new listeners.

`concurrency` is applied per queued start, counting running jobs of the same name. Use the same positive limit for all starts of a name when you need a consistent cap; it is not a global pool shared by different job names. `env` merges extra values into the child's inherited environment.

## The job context

| | |
| --- | --- |
| `ctx.progress(fraction, message?)` | Clamps progress to 0–1; ordinary page snapshots are coalesced over 50 ms. An omitted message becomes `null`. |
| `ctx.log(...parts)` | A line in the job's log |
| `ctx.emit(data)` | A custom event for listeners |
| `ctx.signal` | Aborted when the child receives a cancellation message. App quit kills running jobs without first sending that message. |
| `ctx.id` | The job id |

The default export can be synchronous or asynchronous. `HostJob` is supplied by the app's host declarations; `JobFunction` and `JobContext` are also available as type imports from `@svelte-desktop/shell/server`. An undefined result is sent as `null`. Stdout and stderr are captured alongside `ctx.log` output. The server retains up to 200 log entries per job; list/page snapshots include the last 20, and persisted history includes the last 50.

## Threads and processes

Each running job is its own OS process with its own Bun runtime, started by the server and connected over Bun IPC. It has no `host` global; report back with `ctx.progress`, `ctx.log` and `ctx.emit`. See [Threads and processes](/native/threads).

A thrown error marks the job `failed`, unless cancellation was already requested: then it ends as `canceled`. If the process exits before reporting completion, the registry records a failure with its exit code; a child crash does not terminate the parent app. There is no automatic retry. Cancellation is cooperative: a CPU-bound function must yield to let the child receive its abort message, and must check `ctx.signal`. If a canceled job returns normally before the kill attempt, it can still finish as `done`.

On normal app quit, server cleanup kills tracked running jobs and records them as `canceled` with `error: 'app quit'`. It does not wait for cooperative job cleanup or send an abort first. Do not rely on a job's `finally` block to run during app quit or forced termination. Queued work is not a durable queue and is not resumed on the next launch.

## Development, packaging and history

In `vite dev`, Bun imports the source file through the job runner. Each new job sees the current source; an edit does not reload a running child. In a built app, the adapter embeds each job and its IPC runner. Starting a job launches the app's own executable with `SVELTE_DESKTOP_JOB`, without needing an external Bun installation or the Bun CLI, including with `build.trim`.

Entry names may contain letters, numbers, underscores and hyphens, and end in `.ts` or `.js`. Subdirectories are not discovered. Jobs build as standalone Bun modules outside the SvelteKit/Vite pipeline; use ordinary imports rather than assuming SvelteKit aliases are available.

Packaged apps keep up to 200 ended jobs in `jobs.json` inside `host.paths.data`. They restore with `restored: true`. Results, errors and recent log lines are retained, but jobs are not restarted. Writes during a run are delayed by 200 ms; normal shutdown flushes ended records. Read/write failures are swallowed, so history is best effort. Dev does not bind a history file.

Jobs work on macOS, Linux and Windows. Native libraries or tools a job uses must support the target platform too. See the [jobs reference](/host/data/jobs) for the full API and the [server reference](/host/data/server) for server-only members.
