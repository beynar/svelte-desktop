title: Threads and processes
description: Choose where work runs by what it can block, and how the contexts of an app exchange messages.

An app has several execution contexts: the native UI thread, the Bun Worker that runs your SvelteKit server, the web view's page JavaScript, and any child processes. A promise does not move work to another thread. Choose by what the work can block and who owns its lifetime. For the process layout, see [Architecture](/concepts/architecture).

## Choosing where code runs

| The work is | Run it in | Page |
| --- | --- | --- |
| Short and needs a window, menu or other AppKit object | A Swift, Objective-C or C plugin command (UI thread) | [Plugins](/native/plugins) |
| CPU-heavy or slow, from an existing crate or Go module | A Rust or Go plugin command (own thread or goroutine) | [Rust](/native/plugins/rust), [Go](/native/plugins/go) |
| Python libraries or models | A Python command (own process) | [Python](/native/plugins/python) |
| A synchronous call into existing Node-API code | An addon (blocks the server Worker) | [Addons](/native/addons) |
| Finite, CPU-heavy or long, with progress and cancel | A job | [Jobs](/native/jobs) |
| Long-lived with state and commands | A service | [Services](/native/services) |
| An existing executable | A sidecar | [Sidecars](/native/sidecars) |
| Anything else in TypeScript | Server code, with asynchronous I/O | [Server code](/host/data/server) |

What each context blocks when it is busy:

| Context | A slow task there |
| --- | --- |
| UI thread | Freezes window input, native callbacks and the delivery of every plugin reply and event, even for work already finished elsewhere. Keep handlers short. |
| Server Worker | Stalls all server JavaScript: requests, remote functions and native-event callbacks. Page JavaScript keeps running, but server-dependent actions wait. |
| Page | Blocks that page's event handling and rendering. Calling an `async` function doesn't offload it; send the work to a server endpoint that delegates it. |
| Rust thread, Go goroutine | Only that call. Calls can overlap, so synchronize shared state. |
| Python process | `def` handlers share a pool of threads and `async def` handlers share one loop. See [Python](/native/plugins/python#the-python-process). |
| Job, service or sidecar | Only its own process. A service runs its handlers one at a time, so a long command delays the next. |

Native libraries (plugins and addons) share the app process, so a fatal fault in one can terminate the app. The Rust and Go SDKs catch command panics, but that is not a process boundary. If a crash must be isolated, use a job, service, sidecar or Python.

## Rules

- `async` and `await` do not mean background execution. A synchronous addon function blocks the Worker even when you `await` it.
- Don't compute on the UI thread. Dispatch to a background thread or queue, then reply once. In a C plugin, copy `args_json` before using it after the callback returns.
- Jobs, services, sidecars and extra Workers don't get the server's `host` global. Reach them from server code, and expose them to pages through your endpoints or remote functions.
- Await service sends, inspect a job's terminal state, read sidecar streams and handle failures. A request timeout stops waiting; it doesn't cancel the work.
- Sidecars and threads you start yourself are not stopped at quit. Own their cleanup, for example with `host.onBeforeQuit`. Jobs and services are stopped for you.
- Register page subscriptions in `onMount` and dispose them on unmount. Register save and cleanup hooks before quitting starts (see [`host.app`](/host/app/app)).
- Don't expect events to reach a view showing another origin: native events go to app-origin pages and server code only.

## Messages between contexts

Payloads are JSON. Contexts never share JavaScript objects.

| From | To | Use |
| --- | --- | --- |
| Plugin | Pages and server code | `emit` in the plugin SDK, `host.on` to subscribe. See [events](/host/data/events). |
| Page or server | A plugin | `host.native.<plugin>.<command>()` in either context. See [`host.native`](/host/data/native). |
| Page or server | Every page and the server | `host.broadcast` and `host.onBroadcast`. It doesn't reach jobs, services or sidecars. See [events](/host/data/events#broadcast-between-contexts). |
| Server | Pages | `desktop.publish` and `onDesktopEvent`. See [server code](/host/data/server#messages-to-pages). |
| Job | Server, then pages | `ctx.progress`, `ctx.log`, `ctx.emit`. Pages read them through `host.jobs`. See [Jobs](/native/jobs). |
| Service | Server | `request`, `send` and `port.postMessage`. Forward to pages from server code. See [Services](/native/services). |
| Sidecar | Server | The tool's own streams or protocol. See [Sidecars](/native/sidecars). |

The page bridge only answers the app origin's main frame, and `bridge.allow` can restrict which operations pages call. Server calls aren't restricted by it.

## Bun Workers

The packaged app already runs your server in a Bun `Worker`. The desktop adapter doesn't discover or package additional Worker files, and there is no Worker option in the config: a `new Worker(new URL('./worker.ts', import.meta.url).href)` that works from source isn't evidence the file exists in the compiled app. Use a [job](/native/jobs) or [service](/native/services) when you need an entry embedded in the executable.

A Worker you package yourself has its own globals: no `host`, no platform transport. Exchange messages with its owner through `postMessage` and keep native calls in the owner. It shares the app's failure boundary.
