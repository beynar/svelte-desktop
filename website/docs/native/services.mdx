title: Persistent services
description: Persistent Bun children with bounded messaging, request/reply, optional restarts and quit cleanup.
---

A service keeps state, accepts commands and emits messages in a separate Bun process until stopped. Pick it for an indexer, language server or long-lived worker that you control. Use a [job](/native/jobs) for work that finishes with one result, or a [sidecar](/native/sidecars) for an existing executable with its own protocol.

API reference: [server code](/host/data/server). For finite work and its page-facing state, see [`host.jobs`](/host/data/jobs).

## Define and start a service

```ts src/services/counter.ts
const counter: HostService<{ initial: number }> = ({ initial }, port) => {
  let count = initial;
  port.onRequest((command) => {
    if (command !== 'increment') throw new Error('Unknown command');
    return { count: ++count };
  });
  port.on('message', async (data) => {
    await port.postMessage({ count, echo: data });
  });
  port.signal.addEventListener('abort', () => console.log('stopping'));
  return async () => { /* close databases and other resources */ };
};
export default counter;
```

Start it from server code (an endpoint, remote function or server hook):

```ts
const counter = await host.services.start('counter', { initial: 0 }, {
  restart: { maxRestarts: 3, delayMs: 250 },
});
const off = counter.on('message', (data) => console.log(data));
counter.on('exit', ({ code, signal, restarting }) => console.log(code, signal, restarting));
try {
  await counter.send({ inspect: true });
  const next = await counter.request<{ count: number }>('increment', { timeoutMs: 5000 });
  console.log(next.count); // 1
} finally {
  off();
  await counter.stop();
}
```

This example stops the child after use. For a persistent service, keep the handle in a server module and reuse it across requests. Every `start` creates a separate child; there is no automatic singleton per service name. `HostService` is a global type supplied by the app's generated host declarations. You can instead import `ServiceFunction` as a type from `@svelte-desktop/shell/server`.

## Threads and processes

The service's default export and message handlers run in the child process, not on the UI thread or in the SvelteKit server. In a packaged app, the parent is the app's Bun Worker that hosts SvelteKit. In `vite dev`, the parent is the Vite server process. The parent and child use Bun IPC with JSON envelopes and acknowledgements. See [Threads and processes](/native/threads).

The child has no page `host` global and does not share JavaScript memory with the server. Pages call your endpoint or remote function; the server validates the command and uses the service handle. Return replies through the endpoint, or forward unsolicited messages using server broadcast or WebSocket APIs. Other services and jobs do not share this port; route their messages through the server or use an application-owned protocol. Native UI operations also go through the server.

A child crash does not terminate the parent app. Pending sends and requests reject on exit. Restarts are optional and start fresh child state; they do not replay work. On normal app quit, the server runs its `host.onBeforeQuit` hooks, then stops services and disables restarts. The child also runs its shutdown path when the IPC parent disconnects, including when a dev parent disappears. Forced termination cannot guarantee cleanup completes.

## Lifetime and messaging

`start` resolves after the service's default export initializes. Its optional return value is a cleanup callback. `port.on('message', fn)` accepts async handlers and returns an unsubscribe function; one `port.onRequest(fn)` handles requests, with its return value sent back automatically. Registering another request handler replaces the previous one. Exceptions in a request handler reject that request. Exceptions in message handlers stop the child. `port.postMessage` emits an unsolicited message to the parent; await it when streaming.

| Handle | Behavior |
| --- | --- |
| `name`, `pid`, `state` | Current process identity; state is `running`, `restarting` or `stopped`. |
| `send(data)` | Resolves when the child has consumed the message. |
| `request(data, { timeoutMs })` | Request/reply with internal IDs; rejects after 30 seconds by default. |
| `on('message', fn)`, `on('exit', fn)` | Parent listeners; return unsubscribe functions. Exit events include `code`, `signal`, `restarting`. |
| `stop()` | Disables restarts, aborts `port.signal`, runs cleanup, and force-kills after 500 ms if needed. Repeated calls are safe. |

Messages use JSON values, without transferable ports or handles. Each direction allows one message in flight and at most 64 unacknowledged messages including queued ones; at most 64 requests can await replies. `start` options `capacity` and `maxMessageBytes` change these bounds. The default maximum JSON envelope is 1 MiB. Full queues and oversized/nonserializable messages reject; callers should await sends and handle failures. Child handlers run serially. A blocked handler can stall later commands: use request timeouts and stop the service if recovery requires it. A timeout stops waiting; it does not cancel work already sent. Request type parameters describe expected replies without validating them.

Startup times out after 10 seconds (`startupTimeoutMs`). Restarts are off by default. With a restart policy, each unexpected exit, including exit code zero, can restart with the original arguments, up to `maxRestarts` over the handle's lifetime. Initialization failure ends supervision. State inside the child starts fresh. Pending messages and requests reject on exit and are never replayed; requests during a restart reject. The app owns any durable state or retry decisions. App quit stops and reaps all children, including children awaiting restart. Child stdout/stderr inherit the launching process's output.

## Development and packaging

In `vite dev`, files in `src/services/` run directly with Bun through the service runner. Edits affect new children; they do not reload a running service. Stop and start it to use new code.

In a packaged app, the adapter embeds each service and its IPC runner, then starts the app's own executable with `SVELTE_DESKTOP_SERVICE`. No external Bun installation or Bun CLI is needed, including with `build.trim`. Service files must be directly inside `src/services/`, have names containing letters, numbers, underscores or hyphens, and end in `.ts` or `.js`. They build as standalone Bun modules, outside the SvelteKit/Vite module pipeline; use ordinary module imports rather than assuming SvelteKit aliases are available.

Children inherit the parent's current environment and working directory. Service options configure messaging, startup timeout and restarts; they do not expose custom `env` or `cwd` options. Pass application-specific startup values as `args`.

| Behavior | macOS | Linux | Windows |
| --- | --- | --- | --- |
| Separate Bun child and IPC | Supported | Supported | Supported |
| Embedded runner in the packaged executable | Supported | Supported | Supported |
| Optional restarts and quit cleanup | Supported | Supported | Supported |

Libraries or executables used by a service must also support the target platform.

## Local support bundles

In server code:

```ts
const path = await host.diagnostics.collect({ logs: true, crashes: true, metadata: true });
// Ask the user before sharing. Upload with your application's own transport,
// or return the path to a page and reveal it:
await host.shell.showItemInFolder(path);
```

All three switches default to `true`. Collection creates a private local `.tar.gz` file in `host.paths.cache/support/`; it does not upload it. The application owns review, retention, deletion and upload. Text masking is best effort, so review the archive before sharing. See [the server reference](/host/data/server) for collection options and failures.
