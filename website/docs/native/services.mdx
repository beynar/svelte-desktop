title: Persistent services
description: Persistent Bun children with bounded messaging, request/reply, optional restarts and quit cleanup.
---

A service keeps state, accepts commands and emits messages in a separate Bun process until stopped. Pick it for an indexer, language server or long-lived worker that you control. Use a [job](/native/jobs) for work that finishes with one result, or a [sidecar](/native/sidecars) for an existing executable with its own protocol.

API reference: [`host.services`](/host/data/services). For finite work and its page-facing state, see [`host.jobs`](/host/data/jobs).

## Define and start a service

```ts src/services/counter.ts
const counter: HostService<{ initial: number }> = ({ initial }, port) => {
  let count = initial;
  port.onRequest((command) => {
    if (command !== 'increment') throw new Error('Unknown command');
    return { count: ++count };
  });
  port.on('message', async (data) => {
    await port.postMessage({ count, echo: data });
  });
  port.signal.addEventListener('abort', () => console.log('stopping'));
  return async () => { /* close databases and other resources */ };
};
export default counter;
```

Start it once from a server module and reuse the handle in your endpoints. `host.ready` runs its callback only inside the desktop app, so under a browser-only `vite dev` the service never starts:

```ts src/lib/server/counter.ts
let counter: Awaited<ReturnType<typeof host.services.start>> | undefined;

host.ready(() => {
  host.services
    .start('counter', { initial: 0 }, { restart: { maxRestarts: 3, delayMs: 250 } })
    .then((handle) => {
      counter = handle;
      handle.on('message', (data) => console.log(data));
      handle.on('exit', ({ code, signal, restarting }) => console.log(code, signal, restarting));
    })
    .catch((err) => console.error('counter failed to start', err));
});

export async function increment() {
  if (!counter) throw new Error('Counter service is not running');
  const next = await counter.request<{ count: number }>('increment', { timeoutMs: 5000 });
  return next.count;
}
```

```ts src/routes/api/increment/+server.ts
import { json } from '@sveltejs/kit';
import { increment } from '$lib/server/counter';

export async function POST() {
  return json({ count: await increment() });
}
```

`counter.send(data)` delivers a message to the child's `message` handler. The app stops running services when it quits; call `await counter.stop()` to stop one earlier. Every `start` creates a separate child; there is no automatic singleton per service name. `HostService` is a global type supplied by the app's generated host declarations. You can instead import `ServiceFunction` as a type from `@kitop/shell/server`.

## Threads and processes

A service runs in its own Bun child process with no `host` global; pages reach it through your endpoints or remote functions, with the server holding the handle. See [Threads and processes](/native/threads).

A child crash does not terminate the parent app. Pending sends and requests reject on exit. Restarts are optional and start fresh child state; they do not replay work. On normal app quit, the server runs its `host.onBeforeQuit` hooks, then stops services and disables restarts. The child also runs its shutdown path when the IPC parent disconnects, including when a dev parent disappears. Forced termination cannot guarantee cleanup completes.

## Lifetime and messaging

`start` resolves after the service's default export initializes. Its optional return value is a cleanup callback. `port.on('message', fn)` accepts async handlers and returns an unsubscribe function; one `port.onRequest(fn)` handles requests, with its return value sent back automatically. Registering another request handler replaces the previous one. Exceptions in a request handler reject that request. Exceptions in message handlers stop the child. `port.postMessage` emits an unsolicited message to the parent; await it when streaming.

The handle's members (`send`, `request`, `on`, `stop`, `state`) and the `start` options (`capacity`, `maxMessageBytes`, `startupTimeoutMs`, `restart`) with their defaults are in the [`host.services` reference](/host/data/services).

Messages are JSON values, without transferable ports or handles. Full queues and oversized or nonserializable messages reject, so await sends and handle failures. Child handlers run serially: a blocked handler stalls later commands, so use request timeouts and stop the service if recovery requires it. A timeout stops waiting; it does not cancel work already sent. Request type parameters describe expected replies without validating them.

Restarts are off by default. With a restart policy, each unexpected exit, including exit code zero, can restart with the original arguments, up to `maxRestarts` over the handle's lifetime. Initialization failure ends supervision. State inside the child starts fresh. Pending messages and requests reject on exit and are never replayed; requests during a restart reject. The app owns any durable state or retry decisions. App quit stops and reaps all children, including children awaiting restart. Child stdout/stderr inherit the launching process's output.

## Development and packaging

In `vite dev`, files in `src/services/` run directly with Bun through the service runner. Edits affect new children; they do not reload a running service. Stop and start it to use new code.

In a packaged app, the adapter embeds each service and its IPC runner, then starts the app's own executable with `KITOP_SERVICE`. No external Bun installation or Bun CLI is needed, including with `build.trim`. Service files must be directly inside `src/services/`, have names containing letters, numbers, underscores or hyphens, and end in `.ts` or `.js`. They build as standalone Bun modules, outside the SvelteKit/Vite module pipeline; use ordinary module imports rather than assuming SvelteKit aliases are available.

Children inherit the parent's current environment and working directory. Service options configure messaging, startup timeout and restarts; they do not expose custom `env` or `cwd` options. Pass application-specific startup values as `args`.

Services work on macOS, Linux and Windows. Libraries or executables a service uses must support the target platform too.
