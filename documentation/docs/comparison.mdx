## How to read it

- **gpuix is the only row where the UI isn't a webview.** That's the entire
  point — native GPU text/layout at editor speed with Svelte authoring. You
  trade the DOM's thirty years of semantics for a young element model.
- **Electrobun is strictly safer for content/form-heavy apps**: full DOM,
  full SvelteKit, remote functions for free, and it's already packaged.
- The realistic endgame may be **hybrid** — gpuix for perf-critical surfaces,
  or this fake-DOM approach matured into a real renderer package plus a
  purpose-built native component set.

## gpuix-svelte — same idea, different seam

`khromov/gpuix-svelte` isn't a platform alternative — it's the *same*
Svelte→GPUI bet, executed narrower and cleaner. The meaningful differences:

- **The seam.** They use Svelte's unreleased custom-renderer API (vendored,
  pinned to the PR branch) — no DOM emulation exists at all. We emulate the
  DOM (gdom) so stock compiler output runs unchanged. Their approach deletes
  the DOM-fidelity tail entirely; ours pays it to buy compatibility.
- **What that buys each side.** `bind:` is *refused by the compiler* on
  custom renderers — every input is manual event plumbing. Third-party
  DOM-compiled components can't run (their shipped JS is baked to DOM
  internals). Ours runs `bind:`, `{@html}`, and source-compatible libraries
  like streamdown unchanged.
- **The native boundary.** They consume the published `.node` read-only —
  the sealed-box problem our renderer-verdict documents. We own the Rust
  renderer: custom element vocabulary (x-button/input/markdown/diff),
  token/theme engine with native re-resolution, AriaProperties.
- **Where they're ahead.** Published npm package + starter + tutorial, hot
  reload, WASM/WebGPU browser target, scripted codesign/notarize — the
  product surface ours lacks. And a 4-case headless suite vs our ~480 checks.
- **Convergence path.** When PR #18042 lands stable, `.native.svelte`
  components could compile through their seam as a second frontend — gdom
  survives for the DOM-dependent paths. The bind: gap is liftable via a
  source-level desugar (`bind:value` → `value` + `oninput`).

Verdict on the sibling: better *packaging of the renderer slice*; not a
platform. It validates the direction without obsoleting the broader
SvelteKit/Bun/native-services goal this repo is testing.

## Verdict

**GO** — with the ledger above. For a text/app-chrome-heavy tool (editor,
terminal, dashboard) the native path is compelling. For anything that needs
the web platform, the Electrobun build already works today.
