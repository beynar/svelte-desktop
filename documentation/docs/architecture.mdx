## The core idea

Svelte has no host-config API like React's reconciler. It doesn't need one.

Compiled Svelte output talks to **DOM objects**, and `svelte/internal/client`
lazily captures DOM getters (`firstChild`, `nextSibling`, …) **from the global
prototypes at first mount**. So the binding strategy is:

<Steps>
  <Step title="Install fake globals before mount">
    `installGlobals()` puts `document`, `Node`, `Element`, `Text`, `Comment`,
    `DocumentFragment` and friends on `globalThis` — before Svelte's runtime
    initializes. Svelte's own cached getters become ours. Zero patching.
  </Step>
  <Step title="Parse template HTML into fake nodes">
    `$.from_html` templates feed a mini HTML parser; each component instance
    `cloneNode`s its subtree. Prototypes cost no native ops.
  </Step>
  <Step title="Materialize lazily into native ops">
    Ops emit only when a subtree lands under the mounted root. Comment anchors
    (`{#if}`/`{#each}` boundaries) stay pure-JS; `insertBefore` anchors resolve
    forward to the next materialized sibling.
  </Step>
  <Step title="Feed native events back through Svelte">
    GPUIX events resolve `elementId → fake node`, then dispatch into Svelte's
    own `handle_event_propagation` with a synthesized `composedPath`. Real DOM
    semantics — nothing reimplemented.
  </Step>
</Steps>

## The mutation protocol

Fake-DOM structural changes become JSON op batches on
`renderer.applyBatch` — the same ops `@gpuix/react`'s reconciler emits:

```ts
emit('createElement', id, nativeTag);
emit('setStyle', id, { display: 'flex', flexDirection: 'column' });
emit('setText', id, node.data);
emit('appendChild', parentId, childId);
emit('setEventListener', id, 'click', true);
emit('setCustomProp', id, 'value', text);
emit('setRoot', rootId);
```

Elements map through a tag table — known GPUIX tags pass through, everything
else degrades to `div`:

```ts
const GPUIX_TAGS = new Set([
  'div', 'text', 'img', 'svg', 'canvas', 'input', 'textarea',
  'anchored', 'code', 'diff', 'markdown', 'virtual-list',
]);
```

`input[type=checkbox|radio]` is the one deliberate remap: gpuix's `input` is a
text editor with no click event, so toggles become clickable `div` boxes with
an activation behavior (click → toggle `checked` → dispatch `input` +
`change`), which is what `bind:checked` / `bind:group` listen for.

## The second backend: QuickGUI

The op stream is backend-agnostic — proven by `qg-backend.ts`, which consumes
the *same* ops through `@quickgui/native`'s retained-tree API instead of
`applyBatch`. The mapping is mechanical:

| our op | quickgui call |
|---|---|
| `createElement(id, tag)` | `new NativeNode(NativeNodeTag.X, "", id)` (closed 26-tag vocabulary; our `text` element = their `Text` node) |
| `setText` | `replaceNativeText(node, v)` |
| `setStyle` / `setCustomProp` | `setNativeProperty(node, PropertyCode[k], normalize(v))` — px→number, colors→`parseColor` |
| `setEventListener` | `setNativeEventListener(node, type, cb)` — listener-presence flags (`ClickListener`, `FocusListener`…) |
| `appendChild` / `insertBefore` | `insertNativeNode(parent, child, anchor)` — reparenting is a native **move**, not destroy+recreate |
| `destroyElement` | `removeNativeNode(parent, child)` |
| `setRoot` | `insertNativeNode(window.root, node)` |
| `setWindowKeyEvents` | `keydown`/`keyup` listeners on the root (events bubble up) |

Live mode matches their production model: `runHost()` owns AppKit on the main
thread, the app + Svelte + our fake DOM run in a **Bun worker**, and `Window`
itself is the `NativeNodeHost`. Headless mode needs no dylib at all — a pure-JS
`RecordingHost` satisfies the host contract and the retained `NativeNode` tree
is directly assertable.

:::warning
The QG worker/host split has one sharp edge: **worker exit while the host
holds FFI notifier callbacks segfaults the Bun host** (null deref @0x8).
Multi-window sessions must close windows and exit the host process together —
`app.destroy()` from a worker timer races the dispatch pump. See
[native layer](/native).
:::

## Multi-window — one tree, many roots

The native backend hosts N real NSWindows over a single shared
`RetainedTree`. Element ids stay globally unique; what differs per window is
which *root* it renders:

- `RetainedTree.roots: BTreeMap<windowId, rootElementId>` — `setRoot` binds a
  subtree to a window (`['setRoot', id, w]`; absent `w` → window `0`). The
  binding validates both sides: unknown window or element → batch error,
  and a root can't serve two windows at once (moving unbinds the old one).
  Destroying any subtree removes root bindings anywhere inside it.
- `WINDOWS` registry — `windowId → {handle, label, close_veto}` — owns
  lifetime: `GpuixView::drop` removes its row, unbinds its root, drains its
  window-tagged paint state, and emits `closed {windowId}`. Ids are
  monotonic (`NEXT_WINDOW_ID`), allocated only after `window.create`'s
  options fully validate.
- `GpuixView.window_id` — each view knows its window; every emitted event is
  stamped with it at the single callback seam (`EventPayload.windowId`).

Because gpui paints each window in a separate `render`, process-local paint
state would let one window clobber another's mid-flight data. The split:
state keyed by *globally-unique element id* stays flat (`HashMap<u64, _>`)
but each entry carries its owner window id; per-frame resets and per-window
drains partition on that tag. Covered: scroll handles, virtual-list states
+ pending scrolls + reported anchors, automation bounds, text-selection
registries (`START_REGIONS`/`PAINTED`/`HIGHLIGHTS`), search ordinals. A
paint-side `PAINT_WINDOW` cell lets callbacks resolve the owning window
without threading `window_id` through every builder. Selection state is
per-view (`SharedSelection` is not shared across windows — a press armed in
one window can't promote on a drag in another); the `AutomationClock` is
the one deliberate share — one `Arc` cloned into every view so
`clockPause` freezes all windows for automation.

Op routing follows scope:

- **app-scoped** (`window.create`/`list`/`get`, clipboard, theme) — run
  through the GPUI app context or the `WINDOWS` registry; they work with
  zero windows open and ignore `args.windowId`.
- **window-scoped** (`window.setTitle`, `focus`, `close`, …) — explicit
  `windowId` (validated: non-negative integer, live window) or the key
  window when absent.
- **element-scoped** (`focusElement`, `scrollTo`, `setWindowKeyEvents`) —
  `tree.window_of(element_id)` walks ancestors to the owning root, then the
  update runs inside that window's view.
- **input simulation** (`simulateClick` & friends) — optional trailing
  `windowId`; default is the key window, matching where real input lands.

On the JS side, one `gdom` document hosts every window's subtree:
`createWindowRoot(windowId)` materializes a flagged mount element whose
`setRoot` binds the subtree; `windowRoots` tracks every root (primary
included) so `closed` can dematerialize the right subtree through normal
`destroyElement` ops.

## The transport decision — measured, not argued

Two live transports exist in the tree, which made the architecture choice
measurable:

| Path | Mechanism | Call cost | Verdict |
|---|---|---|---|
| `@gpuix/native` | NAPI-RS addon, in-process | ~44 ns | **primary renderer** |
| `@quickgui/native` | `bun:ffi` → `dlopen` + event-notifier callback | ~13 ns | services + multi-window |
| `$native` | `bun:ffi` → your cdylib, generated bindings | ~18 ns | app-owned Rust code |

A serialized sidecar was evaluated and rejected: at these overheads the
deciding factors are lifecycle and packaging, both of which in-process wins.
`applyBatch` itself is not the bottleneck — 10k ops ≈ 0.68 ms, a 10 MiB
payload ≈ 1.9 ms, idle event drain ≈ 0.1 µs.

## Accessibility metadata

The DOM→native path carries semantics, not just paint:

- **Implicit roles** — `gdom` maps tag (+`type`/`href`) → ARIA role at
  materialization: `button`→button, `h1-6`→heading+`aria-level`,
  `input[type=checkbox]`→checkbox, `a[href]`→link, `nav`/`main`/`table`…
  An explicit `role` always wins; changing `type` re-derives it.
- **Typed aria** — `aria-checked`/`aria-hidden`/… emit booleans,
  `aria-level`/`aria-valuenow`/… emit numbers (not strings) into
  `setCustomProp` — verified in the retained tree via `getTreeJson`.
- **nkit authors semantics** — 24+ components emit `role`/`aria-*` themselves
  (`Switch` → `role="switch" aria-checked`, `Slider` → `role="slider"
  aria-valuenow/min/max`, `Tabs` → tablist/tab/tabpanel…).

What this does **not** yet do: gpuix never materializes those props into the
platform AX tree (`NSAccessibilityElement`). QuickGUI ships a full AX
subsystem — landmarks, style groups, display-preference queries — but only
for its own widget descriptors, which nkit doesn't emit. Transport done;
platform materialization is the open gap (see [limitations](/limitations)).

## The reentrancy rule

:::danger
**Never `applyBatch` inside the native event callback.** GPUI panics on
reentrant `GpuixView` updates — events arrive on a ThreadsafeFunction while the
view may be mid-update. This was found the hard way: a Rust abort, exit 134.
:::

All ops queue and flush on a **macrotask** (`setTimeout`, deliberately not
`queueMicrotask`). Two deferral queues exist because of it:

- `deferCall` — native calls safe at flush time.
- `deferAfterRender` — calls needing a rendered frame, e.g. `focusElement`:
  gpuix only creates a `FocusHandle` for an element that registered focus/key
  listeners *and* has painted once.

## Events, both directions

DOM → native is a table; native → DOM is its inverse plus the window sentinel:

```ts
click → 'click'    mousedown → 'mouseDown'   input → 'change'
keydown → 'keyDown'   scroll → 'scroll'   …
windowKeyDown → 'keydown'   // sentinel elementId, routed to document listeners
```

Three subtleties the suite surfaced:

1. **Delegation is a tree-level set.** Svelte registers delegated types on
   `document` — the bridge sends ONE `setDelegatedEvents` op carrying the
   type list, and the renderer attaches the matching listeners at build
   time (`element.events ∪ delegated`, so per-element ops and delegation
   compose). Text elements are exempt — a DOM text node is never an event
   target, so a press inside `<a>` emits from the anchor and the JS
   activation walk (`<a href>` → `goto`, submit buttons) sees a real
   element. Focus/key types stay element-scoped (focusables only).
2. **Focus needs listeners.** A text `input` that never registers
   focus/key listeners gets no `FocusHandle` — it's unfocusable, so it
   receives no keystrokes. Materialization registers the full set.
3. **`change` ≠ `change`.** gpuix fires `change` per edit; DOM semantics want
   `input` then `change`. The bridge dispatches both, in browser order, with
   `payload.value` applied to `e.target.value` first — which is what makes
   `bind:value` work.

## The class → style bridge

Svelte compiles scoped `<style>` blocks to hashed class attributes +
`append_styles` calls into `document.head`. The fake DOM honors that path:

- `<style>` elements' `textContent` is parsed into a `class → {prop: value}`
  registry keyed on the last class in each selector (Svelte's scope hash).
- Setting `el.className` looks the classes up and merges them into the
  element's style props → `setStyle` op → **scoped CSS actually paints**.

This is the *runtime-injection* lane (dynamic `<style>` elements) — a
compound-selectors-only mini-parser kept deliberately small so the app
bundle doesn't carry a CSS parser. The *compile-time* lane is different:
the vite plugin extracts `<style>` blocks, parses them with Lightning CSS,
and ships `stylesheet.register` ops — the Rust `StyleSheetRegistry`
resolves compounds, all four combinators, attribute selectors, `:not`,
and pseudo-state buckets natively. See [limitations](/limitations).

## The `svelte` client-entry seam

One non-obvious fix: under Bun, `import { mount } from 'svelte'` resolves the
**server** entry (no `browser` export condition) — `mount` throws
`lifecycle_function_unavailable` and `setContext` silently no-ops.

The POC fixes it two ways, both in `build.ts`: a post-compile rewrite of
`from 'svelte'` → a client shim, plus a deep import into
`svelte/src/index-client.js`. In a real package this is a bundler-plugin
alias — see [roadmap](/roadmap).

## The kit layer: SvelteKit semantics in-process

`src/kit/` implements the kit *contract* without HTTP: file-based routes
(`+page.svelte` / `+page.ts` / `+page.server.ts` / `+layout.*` / `+error.svelte`
scanned by `build.ts` → a generated manifest), a `Router` owning the reactive
`page`/`navigating` state, and `goto`/`invalidate`/`depends`/`redirect`/`error`
with the same thrown-object protocol as `@sveltejs/kit`.

```
src/routes/**/+{page,layout}.{svelte,ts} + hooks.ts
        ↓ build.ts scan + compile
gen/routes/manifest.js — deduped layout levels + per-level +error boundaries
        ↓
Router.executeChain — hooks.handle wraps each navigation once
        ↓ reactive router.levels
Shell.svelte — recursive self-import renders layout>…>page via children
```

Fidelity details that mattered:

- **`handle` wraps the navigation once**, like a real request — `locals` set
  there are visible to every `*.server.ts` load in the chain (verified by
  fixture).
- **Layout persistence is data-level, not just visual.** The manifest dedupes
  layout levels by directory so the same level object appears in sibling
  routes; on navigation a kept layout's `load` does not re-run — matching kit,
  where layouts only re-run when their *used* params change (tracked per-load
  via a `Proxy` on `params`).
- **Error boundaries are positional.** A throw at level N renders that level's
  `+error.svelte` inside the layouts that already loaded — a dir's boundary
  catches its page and deeper levels, never its own layout's failure.
- `invalidate(key)` re-runs only levels whose `depends(key)` matched (or
  whose `fetch` hit that URL — fetches are tracked per level) — and goes
  back through `handle` (fresh request ⇒ fresh `locals`), which is the part
  kit gets right and naive ports get wrong.
- `<a href>` interception lives in gdom's dispatch path — an un-prevented
  click on an anchor (or descendant) calls `goto` — so links work without a
  URL bar. `<form>` works the same way: a submit-button click bubbles a
  cancelable `submit` event carrying `.submitter`; the router's document
  listener runs the matching `?/action` (or `use:enhance`'s pipeline first)
  and lands the result on `page.form` via `applyAction` — then re-runs the
  load chain on success, like kit's post-action invalidation.
- `event.fetch` inside loads resolves `+server.ts` endpoints in-process
  (method + params from the same pattern matcher) *before* falling through
  `handleFetch` → real `fetch`. `event.request` is a real Bun `Request`.
- Full segment syntax: `[...rest]`, `[[optional]]`, `[p=matcher]` (against
  `src/params/*.ts`), `(group)` dirs. `hooks.reroute` remaps url→route-id;
  `hooks.transport` encode→decode-round-trips custom classes in server data.
- `page` is a facade over a `$state` store — `page.url` is stored as an href
  string and rebuilt per read, because a `$state`-proxied `URL` silently
  breaks `.search` (internal slots don't survive the proxy).
- Navigations are coalesced by sequence token — a superseded `goto` abandons
  before commit. `pushState`/`replaceState` write shallow history entries
  that `back()` restores without running loads.

## The owned renderer: `native/` (`sgfx`)

`@gpuix/native` is a prebuilt binary — its element vocabulary is compiled in.
To own that vocabulary (a native `x-button` instead of ~6 ops per component),
`native/` builds the gpuix Rust sources as **our own NAPI cdylib**:

- **Source**: gpuix `packages/gpuix/native/src` ported in place (~18k lines:
  retained_tree, element_tree, renderer, style, custom_elements, a11y,
  automation, test_renderer, text, markdown, diff, theme, motion, updater).
- **GPUI dep**: the pinned `remorses/zed` fork (`81c99f8`) **via git deps** —
  no submodule checkout needed. Crates.io `gpui 0.2.2` was tried and failed
  with 235 errors: it keeps the embedded-platform APIs gpuix needs
  `pub(crate)` (`MacPlatform::new_embedded`, `Application::with_platform`,
  `run_embedded`, `VisualTestAppContext`, `open_offscreen_window`). The fork
  is a hard requirement, not a preference.
- **Toolchain**: Rust **1.97.1** (`native/rust-toolchain.toml`) — the fork's
  unconditional `profiler` module uses `std::hint::cold_path`, stable only
  there. `cargo check` ~21s warm; `cargo build --release` ~4min cold, ~42s
  incremental.
- **Output**: `target/release/libsgfx.dylib` → renamed `sgfx.darwin-arm64.node`
  (~23 MB) — a drop-in for the published `.node`. Swap test: copying it over
  `node_modules/@gpuix/native-darwin-arm64/` ran **45/45 + 30/30 + 49/49 +
  11/11** identical.

### `x-button` + the Rust `Recipe` engine

`custom_elements/x_button.rs` registers the first single-element component.
A `<x-button variant="danger" disabled>` in Svelte is **one retained node and
one render dispatch** — the label, states, and `Role::Button` live in Rust:

- `disabled` suppresses events *natively* (verified: click → event; disabled
  → zero events) and dims via `opacity`, not a JS flag.
- `role: "button"` is materialized by the element itself (explicit props win),
  so the AX tree doesn't depend on the JS implicit-role map.
- JS styles still layer on top via `custom_surface` — native defaults,
  author overrides.

`recipe.rs` is the CVA engine those elements are authored against — the same
`{ base, variants, defaultVariants, compoundVariants }` config shape and
resolution order as nkit's `recipe()`, implemented in Rust over `StyleDesc`.
Every authored element declares its recipe; the wire then carries only
variant *names* (`setCustomProp(id, "variant", "danger")` ≈ 30 bytes)
instead of re-serialized style objects on every prop change. Resolution is
cached per effective-variant tuple, so steady-state render cost is one hash
lookup. Nested `hover`/`active` substyles merge key-wise and apply through
the same `apply_interactive_styles` path as wire styles.

`tokens.rs` is the design-token language those recipes are written in — a
closed vocabulary mirroring svelai's (`nkit/tokens.js`), with its resolved
hex palettes kept verbatim:

- **Colors**: `<name>[-<role>][/<alpha>]` — palette entries
  (`primary secondary danger success warning info neutral`), `surface-*`,
  and the `color` ctx placeholder (element's own `color` prop → theme
  `defaultColor`). Roles: `base dark light lighter muted contrast readable
  muted-readable`. `primary/20` composes alpha; literals pass through.
- **Sizes**, per field kind: spacing (`xs sm md lg xl layout-*`),
  `fontSize` (`xs..3xl`), `borderRadius` (`none..full`), dimensions
  (`full auto control-sm|md|lg`). Raw numbers stay px — the ×4 tailwind
  convention is deliberately not imported.
- **Theme scope**: any element's `theme` custom prop
  (`{mode, palette, colors, defaultColor, spacing, text, radius, control}`)
  overrides `Inherited.tokens` for itself + descendants — a Svelte `Theme`
  component is a façade over that one prop. Theme identity is a unique id
  so recipe caches never hit stale resolutions.
- **Deferral + retheme**: JS emits token *names*, never resolved values
  (`backgroundColor: "secondary"` crosses the wire verbatim). The retained
  tree stores both the interned `StyleDesc` and the raw unresolved payload
  (`style_raw`); a `theme`/`color` prop change — or a reparent into a
  differently-themed subtree — triggers `retheme_subtree`, which re-resolves
  descendants against the new chain. Scoped retheme is free; only a global
  `<Theme>` swap still bumps the JS revision counter (which is how Svelte
  `$derived` styles recompute anyway).
- **`data-color` ctx bridge**: svelai writes `data-color` on every ctx
  component; we map it (and the `ctxColor` stamp on resolved styles) to the
  `color` custom prop, so `color-*` refs and `data-[color=x]` conditionals
  see the same value the DOM would.
- **`data-highlighted`** (svelai's virtual-focus attribute) applies the
  `hover` bucket eagerly — the state-layer fill menus paint on
  keyboard-highlighted items.

Because `color` is a ctx prop, `variant` only encodes *shape*
(solid/outline/soft/ghost/link) — svelai's model, and the reason a
`<x-button variant="soft" color="danger">` needs zero compound variants.
Verified live: a `theme:{defaultColor:"danger"}` wrapper restyles its whole
subtree; an element's own `color` prop wins locally. `cargo test` covers
color refs, alpha, per-field resolution, overrides, and cache correctness
(253/253 lib tests). A four-reviewer adversarial pass over this engine —
palette derivation, the deferral wire, cascade semantics, the x-button
recipe — landed 46 findings; all fixed or documented in
`.agent/ADVERSARIAL-THEME.md`, with `packages/tests/probe-adversarial.ts`
(27 checks) as the regression harness.

This is the pattern for the real component set: native elements where the
semantics/states/perf matter (`x-button`, `x-input`, `x-switch`…), JS
composites where composition is the point.
