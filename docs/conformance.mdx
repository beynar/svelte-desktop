## Methodology

Each case is a standalone `.svelte` fixture in `src/cases/`, compiled by
`build.ts`, mounted fresh into a `TestGpuixRenderer` (gpuix's GPU-backed
offscreen renderer), **driven through real GPUI input** — `simulateClick` at
automation-tree coordinates, `simulateKeystrokes`, `simulateScrollWheel` — and
asserted on `getPaintedText()` / the retained tree. No synthetic DOM events;
if a feature passes, the whole loop round-tripped through Rust.

```sh
cd gpuix-poc
bun build.ts               # compile fixtures → src/gen/cases/
bun src/conformance.ts      # → 45/45 pass (gpuix TestGpuixRenderer)
bun src/conformance-qg.ts   # → 45/45 pass (quickgui RecordingHost, pure JS)
bun src/kit-conformance.ts  # → 49/49 pass (kit layer: loads, hooks, nav)
```

:::warning
Only the headless `TestGpuixRenderer` is used for gpuix testing.
`simulateClick` on the live `GpuixRenderer` reenters GPUI mid-update and
panics — the live window is for looking at, not driving.
:::

## Two backends, same cases

`conformance-qg.ts` runs the identical fixture set through the QuickGUI
backend. The differences are honest ones about *where assertions land*:

- **Driving**: gpuix tests use real hit-testing (`simulateClick` at text
  bounds). QuickGUI's JS host has no automation API (their `TestContext` is
  Rust-side), so `conformance-qg` synthesizes events by invoking the wired
  `NativeNode` listeners — the exact callbacks the Rust core calls live.
- **Asserting**: `painted()`/`tree()` read the retained `NativeNode` tree
  (text + tag structure) rather than a paint buffer.
- **Layout-dependent cases** (`bindsize`, `stylecss`, `scroll`): quickgui
  exposes **no JS-side layout readback** — no `getElementBounds`, no
  `getScrollOffset`, no automation tree. Those cases assert the property
  reached the native tree instead of a measured pixel result.

## What 45/45 + 49/49 does and doesn't mean

<Badge variant="success">Proven</Badge> The Svelte **authoring** API surface:
language features, runes, bindings, events, transitions, the tested browser
APIs. The compiler/runtime seam is viable.

<Badge variant="warning">Not proven</Badge> "Any Svelte code": untested DOM
methods, elements without native mappings, untested browser APIs, and the
kit APIs still outside the layer — cookies, request abort, real multi-window
session semantics, service workers, prerendering. New features get added as
fixtures, not assumed.

## Adding a case

<Steps>
  <Step title="Write the fixture">
    Drop `src/cases/thing.svelte` — a minimal component exercising the feature.
  </Step>
  <Step title="Register a driver">
    Add `{ name, drive, expect }` to the cases array in `conformance.ts` —
    `drive` uses `clickText`/`clickType`/`type`/`pump`, `expect` checks painted
    text or the tree JSON.
  </Step>
  <Step title="Run">
    `bun build.ts && bun src/conformance.ts`. If it fails, the gap is real —
    implement it in the fake DOM, never in Svelte.
  </Step>
</Steps>
